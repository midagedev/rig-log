# 2026-11-24

워크스테이션과 Spark를 ConnectX로 직결했다. 처음엔 한 방향만 선로 속도가 나왔고, Spark가 펌웨어 점검 도구 때문에 한 번 죽은 뒤 재부팅하자 양방향 모두 선로 속도가 됐다.

<a name="cx-link"></a>
## 워크스테이션–Spark ConnectX 100GbE 직결

11-16에 산 ConnectX-5 Ex(Dell 펌웨어 16.31.1014, PCIe Gen4 x16)를 워크스테이션에 꽂았다. QSFP28 패시브 DAC 1 m로 포트 1을 Spark의 ConnectX-7 포트 0에 이었다. 링크는 양쪽 100 Gb/s, RS FEC로 바로 올라왔고 드라이버도 따로 깔지 않았다. 커널 내장 `mlx5_core`가 RoCE까지 처리하고, 워크스테이션에는 시험 도구(`rdma-core`, `perftest`)만 설치했다. 양 끝에 새 /30과 MTU 9000을 주었다(`configs/01-lan.yaml`의 `spark-cx`, `configs/spark/90-NM-spark-ws-cx.yaml`). 10GbE 직결 선은 공유기로 옮겼고, Spark 인터넷은 그 유선을 쓴다(`configs/spark/90-NM-lan-wired.yaml`). NFS `/data`도 ConnectX로 옮겼다.

측정은 [`tools/spark/cx-link-test.sh`](../tools/spark/cx-link-test.sh)로 했다(임대 밖 링크 점검, 워크스테이션에서 다른 세션의 빌드가 코어 하나를 씀). 단위는 Gb/s다.

| 방법 | ws → Spark | Spark → ws |
|---|---|---|
| iperf3 TCP 1 / 4 / 8 스트림 | 33.0 / 95.9 / 99.0 | 14.1 / 13.4 / 12.5 |
| RDMA write, QP 1 / 4 | 98.0 / 98.0 | 14.1 / 14.6 |
| RDMA send, QP 1 / 4 | 98.0 / 98.0 | 13.9 / 14.5 |

RDMA read도 같다. 데이터가 Spark에서 나가는 방향만 98.0이 아니라 14.1–14.4였다. Spark 포트의 두 PCIe 절반(각 Gen5 x4) 모두 14.0–14.5였다. 이 방향 전송 중에 일시정지 프레임, 수신 드롭, 버퍼 부족, PCIe 정체 카운터는 모두 0이었다. 받는 쪽이 밀린 것이 아니라 Spark가 천천히 보낸 것이다. 워크스테이션 카드의 `tx_pci_signal_integrity`는 57에서 시작해 그 방향 시험 한 번에 1 늘었다. 7배를 설명하기엔 작다. ~~가설은 SMMU 변환이 송신 DMA를 묶는다는 것이다.~~ 정정: 재부팅으로 풀렸다([아래](#spark-cx7-hotplug)).

지연은 ws가 보내고 받는 왕복이다(µs, p50 / p99).

| 크기 | RDMA write | TCP 핑퐁, MTU 9000 | MTU 1500 |
|---|---|---|---|
| 64 B | 1.31 / 1.37 | 12.6 / 16.9 | 16.4 / 28.1 |
| 8 KiB | 4.80 / 5.07 | 22.5 / 29.9 | 22.9 / 35.6 |
| 16 KiB | 7.80 / 7.97 | 32.3 / 40.9 | 31.1 / 41.4 |

TCP 핑퐁은 Python 양 끝이라 상한이다. 10GbE 선(64 B 26.5, 8 KiB 50 µs)보다 짧고, Realtek과 달리 점보 프레임이 8 KiB 왕복을 늘리지 않았다.

<a name="spark-mstflint-oops"></a>
## Spark가 NVIDIA 펌웨어 점검 중에 죽었다

시험 직후 23:07:50에 Spark가 Tailscale, Wi-Fi, ConnectX 어디서도 응답하지 않았다. 워크스테이션 쪽 100G 링크는 살아 있었다. 23:13에 스스로 재부팅했다. 지난 부팅의 커널 로그를 보니 `mstflint`가 트리 밖 모듈 `mstflint_access`의 `_vendor_specific_sem` → `pci_read_config_dword`에서 NULL 역참조(주소 0xc3)로 oops를 냈다. 이어서 RCU 정체가 왔고 watchdog이 재부팅했다. 우리 세션은 mstflint를 부르지 않았다. Spark에서 그것을 부르는 것은 NVIDIA의 `/opt/nvidia/spark-ota-check`(OTA 펌웨어 점검)와 `nvidia-spark-mlnx-firmware-manager.service`다. 10초 전에 root가 PackageKit을 깨운 기록이 있어 OTA 점검으로 보이지만, 부모 프로세스는 로그에 없다. 재부팅 후 부팅 때 돈 firmware manager는 정상 종료했다. 같은 점검이 다시 돌면 재발할 수 있다. CX-7에 케이블이 생긴 뒤 처음 돈 점검인지는 모른다.

틀렸던 것: 응답이 끊긴 처음 몇 분 동안 우리가 막 지운 임시 주소나 Wi-Fi 변경을 의심했다. 커널 로그가 있는 기계에서는 그것부터 읽는다.

<a name="spark-cx7-hotplug"></a>
## Spark 송신 14 Gb/s는 늦게 붙은 CX-7 상태였다

[위 절](#cx-link)의 14 Gb/s는 Spark가 [oops로 재부팅](#spark-mstflint-oops)된 뒤 사라졌다. 같은 러너를 23:25에 다시 돌린 값이다(Gb/s, 지연은 ws 왕복 µs p50 / p99).

| 방법 | ws → Spark | Spark → ws |
|---|---|---|
| iperf3 TCP 1 / 4 / 8 스트림 | 27.4 / 99.0 / 98.8 | 43.9 / 98.9 / 99.0 |
| RDMA write / read / send, QP 1 | 98.0 / 98.0 / 98.1 | 98.0 / 98.0 / 98.0 |

RDMA write 왕복도 64 B 1.25 / 1.30, 8 KiB 3.18 / 3.39, 16 KiB 4.10 / 4.36으로 재부팅 전(4.80, 7.80)보다 짧다. 지난 부팅은 11-04에 케이블 없이 시작해 `cx7-pcie-hotplug`가 CX-7을 버스에서 내렸고, 오늘 22:14:31 `Cable plugin`에 장치가 다시 붙었다. 그 hot-add에서 mlx5는 "PCIe slot power capability was not advertised"를 찍었다. 케이블을 꽂은 채 부팅한 지금은 같은 장치가 `SlotPowerLimit 75W`와 `RlxdOrd+`로 잡혀 있다. 전원 한도 없는 카드의 절전 동작인지, relaxed ordering이 빠진 탓인지는 케이블을 뽑았다 꽂는 재현 없이는 가를 수 없어 재지 않았다. mstflint의 oops도 이 늦게 붙은 장치를 읽다 났을 수 있다(어느 장치를 읽었는지는 로그에 없다). 규칙은 하나다. CX-7에 케이블을 처음 꽂거나 바꾼 뒤에는 Spark를 재부팅한다.
