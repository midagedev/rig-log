# 2026-11-03

NVIDIA DGX Spark(GB10) 한 대가 들어왔다. 지금까지 이 리포의 Spark 기록은 기여자의 Spark에서 온 것이었고, 오늘부터 같은 측정을 이 장비에서 직접 한다. 오늘은 기계 사실, 상시 접속, 공식 경로의 업데이트, 헤드리스 전환까지 했다.

<a name="spark-arrival"></a>
## DGX Spark 도착과 상시 접속

질문은 둘이다. 이 Spark는 무엇으로 왔는가, 그리고 재부팅 뒤에도 원격에서 늘 붙을 수 있는가.

출고 상태는 DGX OS 7.6.0(빌드 2026-08-27), Ubuntu 24.04.4, 커널 7.0.0-1019-nvidia, 드라이버 580.178.04, CUDA 13.0(nvcc V13.0.88)이다. CPU는 Cortex-X925 10개(최대 3.9 GHz)와 Cortex-A725 10개(최대 2.8 GHz), SMT 없음. `MemTotal`은 127,598,608 kB로, 128 GB 중 약 6.3 GiB가 커널 몫 밖에 있다. `nvidia-smi`는 GB10의 메모리를 `Not Supported`로 보이므로 메모리는 `/proc/meminfo`로 읽는다. 저장장치는 Samsung MZALC4T0HBL1 4 TB NVMe 하나다. 중고로 샀다. 도착 시 NVMe SMART는 전원 63시간, 사이클 30회, unsafe shutdown 7회, 읽기 6.04 TB, 쓰기 2.57 TB, 미디어 오류 0, 수명 사용 0%였다. 루트 파일시스템은 2026-10-10에 만들어졌고 그 뒤 쓰기가 79 GB뿐이라, 대부분의 사용은 재이미징 전 이전 소유자 몫이다.

ConnectX-7이 `lspci`에 없어 처음엔 결함을 의심했다. 부팅 로그를 보면 `15b3:1021` 두 포트가 잡혔다가 `cx7-pcie-hotplug: Cable removal`로 버스에서 내려간다. QSFP 케이블이 없을 때 DGX OS의 `dgx-spark-mlnx-hotplug`가 하는 의도된 동작이다. 두 대를 묶을 때 다시 본다.

접속은 Tailscale SSH(root)로 한다. `tailscaled`는 enabled이고 `RunSSH`, `WantRunning`이 prefs에 저장되어 재부팅을 넘는다. OpenSSH도 `ssh.socket`으로 enabled다. 유휴 절전 타이머는 이미 0이었지만, 메뉴나 버튼으로도 잠들지 않도록 `sleep`, `suspend`, `hibernate`, `hybrid-sleep` 타깃을 mask했다. 무인 업그레이드는 `Unattended-Upgrade "0"`이라 스스로 재부팅하지 않는다. 남은 수동 작업은 둘이다. 노드 키가 2027-05-02에 만료되니 관리 콘솔에서 만료를 끈다. 정전 뒤 자동 전원은 BIOS 설정이라 원격으로 못 바꾼다.

<a name="spark-update-headless"></a>
## 공식 경로 업데이트와 헤드리스 전환

질문은 이렇다. 펌웨어와 OS를 최신으로 올리고, 데스크톱을 끄면 모델이 쓸 메모리가 얼마나 늘어나는가.

경로는 NVIDIA 문서의 CLI 절차(`apt update`, `apt dist-upgrade`, `fwupdmgr refresh`, `fwupdmgr upgrade`, reboot)다. 문서는 Dashboard를 권하지만 헤드리스에서는 Dashboard가 동작하지 않는다는 포럼 보고가 있다. `fwupdmgr`를 보면 EC(0x03000d07)와 UEFI 둘은 이미 최신이고 바뀌는 것은 패키지뿐이다. 492개 중 핵심은 커널 1019 → 1024와 그 커널용 580-open 모듈이다. 드라이버는 580에 남는다. 590·615 드라이버는 포럼에서도 비지원 경로이고, 루트 마운트 실패와 시스템 정지 보고가 있어 손대지 않았다.

헤드리스는 `systemctl set-default multi-user.target`이다. 포럼은 2–3 GB를 추정하지만 잰 사람은 없었다. 그래서 바꾸기 전에 `drop_caches` 직후의 `MemAvailable`을 재 두었다. 데스크톱 상태에 Firefox까지 떠 있었고, 커널 1019에서 **122,432,552 kB**였다. 업그레이드(8분 30초, 패키지 519개)와 재부팅 뒤 커널 1024, 헤드리스, 가동 1분에 같은 방법으로 재니 **125,219,000 kB**였다. 차이는 2,786,448 kB(2.66 GiB)다. 커널과 가동 시간도 함께 바뀌었고 Firefox가 떠 있던 상태와 비교한 값이라, 데스크톱만의 몫으로 분리된 값은 아니다. 재부팅은 51초 만에 SSH로 돌아왔다. 부작용 보고는 둘이다. 하나는 Dashboard가 멈춘다는 것, 다른 하나는 NCCL이 graphical보다 느렸다는 것(한 사용자, 원인 미확인)이다. 후자는 두 대를 묶을 때 잰다. 되돌리기는 `set-default graphical.target`이다.

NVIDIA 플레이북은 unified memory에서 페이지 캐시가 GPU 할당과 다툰다며 모델 로드 전에 `sync; echo 3 > /proc/sys/vm/drop_caches`를 권한다. Spark 러너에는 이 줄을 넣는다. 스왑은 16 GiB 파일, `vm.swappiness` 60 그대로다.

GPU 읽기를 300초 이어 걸자 초당 값이 257.0–257.9 GB/s로 평탄했다. 온도는 39에서 55 °C, SM 클럭은 2554–2600 MHz였고, 클럭 제한 사유는 302샘플 모두 0이었다. 이 부하에서 GPU 전력은 25 W 언저리라 연산을 꽉 채우는 부하는 아직 안 걸었다. PCIe AER 정정 오류는 부하 전후 모두 8건이고, 전부 부팅 때 ConnectX-7을 내리는 13초 안에 났다. 메모리 오류와 MCE는 0이다.

판명된 것. GPU가 혼자 읽으면 258 GB/s다. CPU 20스레드가 같이 읽는 5초 동안 GPU는 217.8–227.4 GB/s로 떨어졌고 CPU는 37.1 GB/s를 얻었다. 합은 약 255–264 GB/s로 GPU 혼자일 때의 천장과 같다. 이 기계에서 CPU 쪽 읽기는 대역폭을 더하지 않고 같은 몫을 나눈다. 워크스테이션의 host tier는 PCIe 너머 별도 DDR4 통로였다.

틀렸던 것. 첫 판의 지속 부하 요약이 최소 0.0을 냈다. `t=  1 s`와 `t=296 s`의 필드 수가 달라 awk가 숫자 대신 단어를 읽은 탓이고, 단위로 숫자를 찾게 고쳤다. 같은 판의 NVMe 원시 장치 `dd` 읽기(12.6 GB/s)는 버렸다. 쓰지 않은 LBA가 섞이면 SSD는 NAND를 읽지 않고 답한다.

## Spark NVMe 읽기, 워크스테이션의 두 배

질문. 모델을 디스크에서 얼마나 빨리 읽는가. 워크스테이션의 [09-12 fio 표](2026-09-12.md#nvme-sustained-write)와 [10-11 큐 깊이 스윕](2026-10-11.md)에 맞춰 쟀다.

fio는 워크스테이션과 같은 하네스 [`configs/disk-bench.sh`](../configs/disk-bench.sh)를 `/var/tmp`에 돌렸다. 32 GiB, O_DIRECT, libaio다.

| fio | Spark 삼성 Gen5 4 TB | WS Phison E18 | WS 980 PRO |
|---|---|---|---|
| 순차 읽기 1M QD8 | **14.89 GB/s** | 6.00 | 7.09 |
| 랜덤 읽기 4K QD32 | **585,469 IOPS** | 152,519 | 138,773 |
| 랜덤 읽기 4K QD1 | 4,884 IOPS, 0.203 ms | 15,836, 0.056 ms | 18,038, 0.048 ms |

큐 깊이 스윕은 [`tools/spark/nvread.c`](../tools/spark/nvread.c)로 했다. 4 MiB blocking pread에 워커 수가 곧 QD이고, 워크스테이션 순서(4, 1, 32, 2, 16, 8)로 세 바퀴를 돌린 중앙값이다. 판명된 것. 순차 읽기는 2.1–2.5배이고 Gen5 x4 원시 15.75 GB/s[유도]의 94.5 %다. Spark는 스레드 하나로도 고원에 가깝다. 반대로 4K QD1 지연은 3.6–4.2배 느리다. 원인(APST, ASPM, CPU 유휴 상태)은 가르지 않았다. fio 시작 증인은 load1 3.00이었는데, 직전에 fio를 설치한 탓이다.

## Spark 다운로드: 한 범위를 두 번 받은 버그

질문. 저녁 다운로드에서 NVFP4 둘이 rc 1로 끝난 이유와, 이미 받은 파일을 믿어도 되는가.

12:20Z쯤 네트워크가 몇 분 끊겼다(TLS handshake timeout, crates.io 접속 실패). 그때 청크 둘이 1,261,982,443 바이트로 끝났다. 기대한 것은 1,250,859,701이다. `curl --retry`는 stdout을 되감지 못한다. 그래서 중간에 끊긴 범위를 다시 받으면 앞부분이 한 번 더 붙는다. 그 뒤에 짧은 읽기가 오면 크기는 맞고 내용은 틀린 파일이 된다. 크기만 보던 [`tools/fetch-gguf.sh`](../tools/fetch-gguf.sh)는 이것을 못 잡는다.

고친 것. curl의 `--retry`를 뺐고, 이어받기는 파일 길이에서 시작하는 바깥 루프만 한다. 넘친 청크는 지우고 다시 받는다. 끝난 파일마다 tree API의 해시와 대조한다(LFS는 sha256, 작은 파일은 git blob sha1). 통과한 파일은 `.fetch-verified`에 적는다. 고친 판으로 spark-fetch를 다시 시작했다.

판명된 것. 이미 받은 파일은 모두 해시가 맞았다. FP4-Local 33개, Qwen3.6 GGUF 2개, Qwen3.8 GGUF 5개다. 그러니 그 위에서 잰 bloomery 테이크도 유효하다. 이미지 당김 루프도 같은 단절에 실패해 놓고 rc=0을 찍었다. 파이프의 rc를 찍은 탓이다. [`tools/spark/pull-images.sh`](../tools/spark/pull-images.sh)로 바꿨다.

<a name="spark-nsys-lag"></a>
## Spark: bloomery가 지는 두 곳을 nsys로 나눔

질문. 첫 표에서 bloomery가 진 두 곳, 곧 Qwen3.6 GGUF 디코드(llama.cpp 대비 −1 %)와 MTP를 켠 긴 프리필(끈 때 대비 −5 %)은 어느 커널에서 오는가.

방법. [`tools/spark/nsys-probe.sh`](../tools/spark/nsys-probe.sh)로 같은 요청 하나를 nsys 아래서 받았다(디코드는 산문 128토큰, 프리필은 4,200토큰). 텐서 크기는 gguf-py로 파일에서 읽었다. 표와 커널 이름은 [`docs/spark-engines.md`](../docs/spark-engines.md)의 "nsys로 나눈 것"에 있다.

| 곳 | 원인 커널 | 크기 |
|---|---|---:|
| 디코드, Q8_0 밀집 1.49 GB/토큰 | `q8_0_gemv` 202 GB/s, llama.cpp 232 GB/s | +0.97 ms/토큰 |
| 디코드, 전문가 down Q5_K | `q5k_gemv_sel` 136 GB/s, llama.cpp 196 GB/s | +0.48 ms/토큰 |
| 프리필, MTP 저장 걷기 | 4,200행을 64행씩 67번(`MTP_STORE_ROWS`) | +63 ms / 4,200토큰 |

판명된 것. 디코드에서 bloomery는 전문가 gate/up(−0.23 ms)과 헤드(−0.14 ms)에서 이기고, Q8_0 밀집과 Q5_K down에서 진다. 커널 합은 16.25 대 15.90 ms다.
`q8_0_gemv`는 행마다 워프 하나가 f32 활성을 그대로 읽는다. 융합도 없다(launch 248회 = Q8_0 텐서 250개). llama.cpp는 활성을 q8_1로 한 번 양자화하고, 같은 입력의 gemv를 묶는다.
프리필 차이 +89 ms 가운데 63 ms는 MTP 저장 걷기다. 걷기는 이미 k·v만 만드니, 헤드 로짓 가설은 틀렸다. 같은 혼합 커널이 본 패스 2,100행에 757 µs, 저장 걷기 64행에 436 µs다. 걷기마다 가중치를 다시 읽는다.

아직 모르는 것. 나머지 26 ms(대상 층 커널이 1–3회씩 더 돈다)의 이유. 그리고 두 제안의 실제 이득은 bloomery 쪽에서 바꿔 재 봐야 안다.
