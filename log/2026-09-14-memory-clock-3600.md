# Memory clock: 3200 to 3600, and where the wall is

**2026-09-14, late evening.** The host-bandwidth work earlier today
([WKS-22](2026-09-14-v41-gap-closed-prefill-and-queue.md)) ended with the read
cap at 131 GB/s and the note that the remaining ~10 % was in the BIOS memory
clock, not in flags. This entry is that step: the DIMMs walked from DDR4-3200
through 3400, 3600, 3666, and three failed attempts above, with the same
probe, stress, identity check and decode run at each stop. The BIOS work was
the user's; the measurements are from the machine.

Everything below is on the same eight Samsung M378A4G43AB2-CWE 32 GB 2Rx8
non-ECC UDIMMs, one per channel, on BIOS 1901 after a defaults reset. The
board is an ASUS Pro WS WRX80E-SAGE SE WIFI; the CPU a 5975WX (four CCDs).

## The chain run at every clock

One script per clock, launched after `llm.service` reported healthy, on a
machine doing nothing else:

1. bandwidth: `bw 32 8 5` pinned to cores 0–31 (read, 8 GiB, best of 5), then
   8 threads on CCD0 and 16 threads on two CCDs, three times each;
2. greedy identity pass A: 20 fixed prompts, `temperature 0`, 64 tokens,
   against the serving port;
3. `stress-ng --cpu 32 --cpu-method matrixprod --vm 8 --vm-bytes 16G
   --vm-method all --verify --timeout 600` — 128 GB of RAM under eight
   pattern writers that read back what they wrote, ten minutes (five at
   3400);
4. greedy identity pass B, compared byte-for-byte with A;
5. three single-stream decodes of 400 tokens on the serving port;
6. MCE/EDAC and PCIe AER counters from the kernel log, before and after.

The `--verify` flag on the memory stress is the part that matters. These
DIMMs have no ECC, so a marginal clock does not raise an error counter: it
returns wrong bytes and says nothing. Only a stress that checks its own
readback can see that.

## What the numbers say

**Clock moved bandwidth one-for-one up to 3600.** 3200 → 3600 is +12.5 % in
clock and +12.6 % in 32-thread read (131.2 → 147.7). The per-CCD figure moved
the same way (40.2 → 44.3), so the four-CCD cap found this morning is a
memory-side cap that scales with the memory clock, not a fabric cap that
would have stayed put.

**3666 was worse than 3600, and then it was wrong.** At MEMCLK 1833 the
32-thread read dropped to 143 while the single-CCD read stayed at 44.3 —
the pattern of the fabric no longer running 1:1 with the memory clock. The
Infinity Fabric clock on this board follows the memory clock automatically
up to 1800 MHz and cannot be set by hand (see below), so 3666 is memory
running ahead of the fabric. Then the ten-minute stress returned:

```
stress-ng: fail:  [6142] lfsr32: detected 46 memory errors
stress-ng: fail:  [6146] lfsr32: detected 54 memory errors
stress-ng: fail:  [6142] rand-set: detected 16 memory errors
stress-ng: fail:  [6145] gray code: detected 8 memory errors
stress-ng: fail:  [6143] gray code: detected 8 memory errors
stress-ng: fail:  [6142] prime-zero: detected 4 memory errors
stress-ng: fail:  [6148] modulo X: detected 2 memory errors
stress-ng: fail:  [6146] prime-zero: detected 1 memory error
stress-ng: info:  [6099] passed: 34: cpu (32) vm (2)
stress-ng: info:  [6099] failed: 6: vm (6)
```

139 wrong readbacks in ten minutes, concentrated in the patterns with the
most bit transitions (LFSR, random), none in the simple ones — the shape of
a timing margin, not of a bad cell. The kernel's MCE and EDAC counters read
0 throughout: non-ECC memory corrupting silently, exactly as predicted this
afternoon. Without `--verify` this clock would have looked like "3 % slower
than 3600 but fine".

**3600 is the edge, so it gets margin.** 3600 passed at the Auto 1.2 V, but
the next step up failed at 1.3 V, which puts 3600 at the boundary of this
IMC with eight dual-rank DIMMs. The DRAM voltage was therefore set to 1.30 V
for the standing configuration — inside the JEDEC/XMP range (1.2 nominal,
1.35 for every XMP kit), no measurable thermal cost on bare UDIMMs, and read
back by the BMC as 1.29/1.28 V on the two channel groups.

**Decode moved less than bandwidth.** 3400 → 3600 is +6 % in bandwidth and
about +2 % in single-stream decode (26.0 → 26.3, inside the run-to-run
band). The decode budget on the served profile has a GPU share and a draft
share that the memory clock does not touch. A clean 3200 decode row was not
taken today (the 3200 figures from earlier were a different prompt and a
three-stream run), so the full 3200 → 3600 decode delta is not claimed here;
it needs one more reboot to 3200 and the same three runs.

## What the firmware does and does not offer

Three things about this board's BIOS were established by trying, because the
manual (E18120) is silent on all three.

**There is no Infinity Fabric clock item.** The consumer boards' Advanced →
AMD Overclocking menu with "Infinity Fabric Frequency and Dividers" does not
exist on this workstation firmware; the manual text contains no "FCLK",
"Infinity" or "UCLK" anywhere, and AMD CBS → DF Common Options holds only
scrubber, NUMA and interleave items. The fabric follows the memory clock 1:1
up to 1800 MHz on its own, and the only readout of whether it did is the
bandwidth probe (there is no sysfs for it on Linux).

**DRAM voltage on Auto is 1.2 V regardless of the memory clock, and does not
move with load.** Setting the memory clock in AMD CBS leaves Ai Tweaker
reading Auto for everything, and Auto meant the SPD default: the BMC read
1.22 V at 3400 and at 3600, idle and under the memory stress alike (VCORE
moved 0.74 → 1.10 V over the same samples). The manual items Ai Tweaker →
DRAM ABCD Voltage / DRAM EFGH Voltage (p.18, 0.500–2.000 V) do apply: 1.30
entered read back as 1.29/1.28 V.

**Memory Clock Speed is a list.** AMD CBS → UMC Common Options → DDR4 Common
Options → DRAM Timing Configuration → Accept → Overclock Enabled → Memory
Clock Speed, values in MEMCLK (half the DDR figure): 1700 = 3400,
1800 = 3600, 1833 = 3666, 1867 = 3733, 1900 = 3800.

## Getting into the BIOS without the keyboard

Both of these worked today, and either is enough:

```
sudo systemctl reboot --firmware-setup      # sets the UEFI OsIndications bit
sudo ipmitool chassis bootdev bios          # BMC one-shot override, next boot only
```

The second also works from outside the host (`ipmitool -I lanplus -H <bmc>
-U <user> chassis bootdev bios`, then `chassis power cycle`) when the OS is
not up.

## Recovering from a clock that does not POST

3800 did not train. The board retried, did not fall back to a safe clock on
its own within the time given, and the physical CLR CMOS button was used. The
BMC's web UI has no remote CMOS clear or BIOS-defaults action — its
Maintenance menu is BMC firmware and BMC settings only — so this recovery
needs hands on the case. A CMOS clear on this board resets everything, and
the list to re-enter afterwards is in
[`docs/wrx80e-bios-setup.md`](../docs/wrx80e-bios-setup.md#after-a-cmos-clear).

## Two things seen in passing

The PCIe AER counter recorded corrected Data Link Layer errors on the root
port of the RTX A6000 (`00:03.1`, two events) during the 3600 run, after the
same class of event on the Samsung NVMe this afternoon. Two devices on
different root ports, both corrected, both while memory was being stressed
— filed under WKS-21 as a pattern to watch, not attributed to the memory
clock.

The air cooler held the package at 62–69 °C through every ten-minute
stress at full boost (about 285 W package), fan at its constant 2200 rpm.
