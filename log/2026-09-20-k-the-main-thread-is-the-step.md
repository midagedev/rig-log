# 메인 스레드가 곧 스텝이다 — SwiGLU 8레인 +4.0%, znver3 +4.8%, 그리고 스텝당 할당 14454번

2026-09-20 밤, [-j](2026-09-20-j-the-lock-at-the-end-of-every-chunk.md)의 61.48 tok/s에서 이어진다. 대상은 같다: DeepSeek-V2-Lite-Chat Q3_K_M, CPU 전용, 32스레드, N=96, 속도 판정은 전부 `just ab-decode`(같은 임대 안에서 직전 커밋과 번갈아 네 바퀴, 바퀴마다 증인)의 상대값이다.

## 먼저 버린 것과 고쳐 읽은 것

**같은 입력을 내용으로 비교해 한 번만 양자화하는 것은 더 느렸다.** 디코드에서 라우팅된 전문가 여섯은 같은 토큰의 사본을 각자 받고, 포인터가 달라 여섯 번 양자화된다. 단일 컬럼 입력을 비트로 비교해 묶었더니 62.83 → 61.03 tok/s, 네 바퀴 모두 패. 왜 느린지는 재지 않았다 — 2048개 float 비교 다섯 번이 메인 스레드의 직렬 일로 얹힌 것이 없앤 사전 패스 디스패치보다 비쌌으리라는 추정뿐이다. 되돌렸다.

**ik를 perf로 봤더니 "내적 8.3 ms가 이상치"라는 전제가 틀렸다.** ik의 llama-bench(t=32, `-e cpu-clock`)는 표본의 75%가 `mul_mat` 커널이고 17%가 장벽 스핀으로 보이는 주소다. 스텝 12.1 ms × 32스레드 × 0.75 ≈ 290 ms의 커널 스레드시간인데, 우리 레벨2의 dot 열(워커 CPU 합)은 266 ms다. 커널은 이미 같은 선이다. 다른 것은 워커 이용률이다 — ik 75%, 우리 51%. 워커가 노는 시간은 메인 스레드가 디스패치 사이에 혼자 일하는 시간이므로, 메인 스레드의 직렬 구간이 그대로 스텝의 길이다.

**perf 함정 셋, 전부 오늘 밟았다.** ① 이 CPU의 기본 이벤트(IBS `cycles:P`)는 심볼 귀속이 엉터리였다 — `-e cpu-clock`으로 다시 떴다. ② `-D 2000`은 시작만 건너뛰고 끝은 안 건너뛴다. 메인 스레드의 `zap_pte_range` 6.4%를 스텝 안의 munmap으로 읽었는데, 콜그래프를 뜨니 `drop_glue<Gguf>` ← `main`, 프리폴트한 8 GB 매핑을 종료할 때 푸는 비용이었다. 리포트를 `--time 25%-85%`로 자른다. ③ 프로파일한 바이너리가 HEAD가 아니었다. 되돌린 디듀프 실험의 바이너리(21:54 빌드)를 소스 되돌림(21:56) 뒤에 그대로 perf에 물렸다 — `box.sh`는 소스만 rsync하고 빌드는 레시피가 한다. 프로파일에 남아 있던 `memcmp` 한 줄이 단서였다(결과적으로 그 memcmp는 `Gguf::find`의 이름 비교였고 수치는 크게 안 움직였지만, 확인 전에는 몰랐다).

## 메인 스레드의 정상 상태

HEAD 바이너리, N=400, 메인 스레드만, 해체 구간 제외:

| 심볼 | 메인 스레드 표본 |
|---|---:|
| `for_each_chunk`(자기 청크 + 장벽) 합 | 52.7% |
| `memset` | 13.5% |
| malloc·free 계열 합 | ~12.5% |
| `swiglu` + `expf` | 8.4% |
| `rms_norm` · `argmax` · `add` · `rope_pair` | ~2% |

절반이 디스패치 안이고, 나머지 절반이 워커 32개가 기다리는 직렬 구간이다. 그 직렬 구간의 절반이 할당과 0 채우기다.

## 세어 보니 스텝당 14454번

perf 비율을 정수로 바꾸려고 세는 할당자를 단 게이트를 만들었다(`tests/alloc.rs`, `just gate-alloc`): 단일 토큰 스텝 하나가 할당자를 **14454번, 24.5 MB** 부르고 그중 11943번이 메인 스레드다. libc `malloc`에 uprobe를 걸어 콜스택과 함께 떠서 호출 지점별로 나눴다:

| 지점 | 스텝당 | 무엇 |
|---|---:|---|
| `matmul_q_multi`와 그 하위 | ~4000 | 호출마다 Vec 여덟아홉 개, 풀 폭의 `ChunkSlots` 둘 |
| `wv_b_heads` | ~2300 | 헤드마다 `format!`한 이름·`dims` Vec·게더 텐서 |
| `Gguf::data` | ~1500 | `ok_or(LoadError{ name: t.name.clone(), .. })` — `ok_or`는 인자를 먼저 평가하므로 성공하는 호출마다 이름을 복제하고 버렸다 |
| `expert_view` | ~1260 | 전문가마다 `TensorInfo`를 새로 만들며 이름 복제 + `dims` Vec |
| 메타데이터 키 `format!` | ~600 | `MlaParams::read`·`Meta::read`가 블록마다, 스텝마다 |
| 텐서 이름 `format!` + `find` | ~400 | |

토큰에 의존하는 것은 하나도 없다. 전부 로드 때 한 번 하면 되는 일을 스텝마다 27번 하고 있었다.

첫 조치는 둘이다. `Tensor2`의 `Drop`이 버퍼를 스레드별 프리리스트에 돌려주고 생성자가 거기서 꺼내며, 전부 덮어쓰는 출력은 0을 채우지 않는다(`Tensor2::scratch`; `BLOOMERY_POISON=1`이면 NaN으로 채워서 안 쓴 칸이 게이트에서 터진다 — 포이즌을 켠 kv·mt·forward·moe·attn 게이트 rc 0). 그리고 `ok_or_else`. 14454 → **11463번, 16.3 MB**. 게이트의 상한 11600은 내려가기만 하는 래칫이다.

**속도는 안 움직였다**: 62.25 대 61.86 tok/s, 잡음 안. 할당의 5분의 1과 memset의 3분의 1을 없앤 값이 기대치로 0.3 ms인데 A/B의 해상도가 그 정도다. 횟수 게이트는 속도의 대리 지표가 아니라 "스텝 안에서 로드 시점의 일을 하지 않는다"는 구조 계약으로 남긴다. 나머지(뷰·메타데이터·이름 조회·호출당 Vec)를 로드 시점 계획으로 옮기는 라운드는 GLM-5.3(effort max)에 위임해 워크트리에서 돌고 있다. 완료 조건은 비트 게이트 전부 rc 0과 `gate-alloc` ≤ 1500이고, 속도는 돌아온 뒤 리드가 잰다.

## SwiGLU를 8레인으로: +4.0%, 발산 집합 {24} → {}

메인 스레드가 전문가마다 libm `expf`를 1408번 부르고 있었다. ik는 같은 자리에서 `ggml_v_expf`(Arm optimized-routines의 다항식)를 AVX2로 8개씩 돈다. 그걸 레인 단위로 옮겼다(`qdot::swiglu`): `x / (1 + exp(-x)) * up`, 8 미만 꼬리는 0으로 패딩한 같은 레인을 지나게 해서 원소의 값이 블록 안 위치와 무관하다(단위 시험이 1413개 원소 각각을 단독 호출과 비트 비교).

상수 아홉 개를 기억으로 적었다가 둘이 틀렸다(`0x1.8p23`과 `0x1.7f7d1cp-20`의 비트 패턴). 원본의 16진 부동소수 표기를 파이썬 `float.fromhex`로 비트로 바꿔 대조해서 빌드 전에 잡았다. 기억으로 적은 상수는 초안이다.

같은 임대 네 바퀴(프리리스트 포함, 직전 커밋 대비): 62.84·62.64·61.95·62.04 → 64.29·65.36·64.66·65.05, **62.37 → 64.84 tok/s(+4.0%)**. 오라클 허용오차 게이트(ffn·moe·forward, 1e-4)와 우리 경로끼리의 비트 게이트(kv·mt·derived)는 그대로 rc 0이고, `gate-prompts`는 **빨갛게 떨어졌다 — 좋은 쪽으로**: ik와 argmax가 갈리던 프롬프트가 {24} 하나였는데 0개가 됐다. 옛 핀으로 실패한 것을 확인하고 빈 집합으로 재핀했다. 프롬프트 24는 ik 마진 0.151짜리 근접 동률이라, 이건 추첨이 ik 쪽으로 떨어진 것이지 나머지 드리프트가 닫혔다는 증거는 아니다.

## `-C target-cpu=znver3`: +4.8%

-j에서 `rintf`를 걷어낼 때 "SSE4.1이 없는 기준 타깃"이라고 적어 놓고 타깃 자체는 안 건드렸다. 저장소에 rustflags가 없었다 — `qdot`의 커널만 `#[target_feature]`로 AVX2였고, 나머지 스칼라 루프(rms_norm, 잔차 덧셈, 게더·스캐터, argmax)는 전부 SSE2로 컴파일되고 있었다. rustc는 fast-math 없이는 곱셈·덧셈을 FMA로 합치지도 환원 순서를 바꾸지도 않으므로 값은 그대로여야 하고, 실제로 플래그 아래서 게이트 열넷이 rc 0이다(열다섯째인 `gate-profile`은 아래).

같은 임대 네 바퀴: 65.09·65.49·64.38·63.87 → 67.46·67.92·68.08·67.73, **64.71 → 67.80 tok/s(+4.8%)**. `.cargo/config.toml`에 `x86_64-unknown-linux-gnu` 타깃 한정으로 넣었다(Mac의 에디터 빌드를 안 깨려고).

`gate-profile`의 커버리지 바닥이 걸렸다: 97.1% → 96.9%, 네 번 중 네 번. 어두운 구간은 0.59 → 0.60 ms로 그대로이고 그 아래의 훅 걸린 일이 0.6 ms 줄어서 비율만 내려간 것이라 바닥을 96으로 재핀했다(귀속 주석에 두 수치). 그 0.6 ms가 바로 위 표의 스텝당 조회와 드롭이므로, 로드 시점 계획 라운드가 끝나면 바닥을 다시 올린다.

## 지금 어디인가

A/B 상대값으로 오늘 밤의 사슬은 61.5 → 64.8 → **67.8 tok/s**다. 헤드라인 러너를 한 번 돌렸지만 조용한 기계가 아니었다 — 위임 라운드가 같은 박스에서 빌드·게이트를 돌리는 중이었고 증인의 loadavg가 2.7 → 5.1이다: bloomery 65.40 tok/s(15.3 ms/token), 같은 임대 ik tg32 82.63 ± 0.13. 그 숫자로는 잔여 1.26배, A/B의 67.8을 같은 ik 값에 대면 1.22배인데 뒤의 것은 다른 임대의 값을 나란히 놓은 것이라 헤드라인으로 쓰지 않는다. 위임 라운드가 끝나고 박스가 빈 뒤에 다시 잰다.

남은 격차 3 ms 남짓의 후보는 측정된 순서대로: 스텝 안의 로드 시점 일(진행 중), 호출당 12–33 µs인 matmul 앞뒤 비용, 그 다음이 디스패치 묶기다. 커널은 건드릴 이유가 없다 — 스레드시간으로 이미 ik와 같다.
