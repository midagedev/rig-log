# 스큐 40%는 타이머였다 — 77.0 tok/s, 잔여 1.075배

2026-09-21 새벽(측정 시각은 9월 20일 15시대 UTC), [-k](2026-09-20-k-the-main-thread-is-the-step.md)의 72.30 tok/s에서 이어진다. 같은 대상, 같은 규약: 속도 판정은 `just ab-decode`의 같은 임대 네 바퀴 상대값이고, 헤드라인 러너는 이제 ik도 우리와 같은 N으로 잰다(-k에서 고친 tg32/tg96 불일치).

## 넣은 것

| 변경 | 같은 임대 A/B (tok/s, 네 바퀴 평균) | |
|---|---|---|
| 항등 버킷이면 전문가 입력으로 `x` 자체를 넘김 + attn·embed 출력을 `scratch`로 | 74.33 → 74.55 | 무차이(3/4) |
| 활성값 양자화기의 AVX2 쌍둥이(q8_K, q8_2_x4) — GLM-5.3 위임 | 74.55 → 75.19 | +0.9%, 4/4 |
| 풀: 파킹한 쪽이 있을 때만 notify, 공유 카운터 대신 워커별 완료 표식 | 77.49 → 77.55 | 무차이 |
| 행 디스패치의 꼬리 훔치기 | 디코드 77.36 → 77.17 / **프리필 92.5 → 115.5** | 디코드 무차이, 프리필 +25% 4/4 |

(같은 커밋이 창마다 2–3 tok/s 움직인다 — 74.5였던 main이 한 시간 뒤 창에서는 77.5다. 그래서 열 사이가 아니라 행 안에서만 비교한다.)

헤드라인(15:16 UTC, 상위 프로세스는 모니터링뿐): **N=96 76.97 tok/s(13.0 ms/token), 프리필 116.68 tok/s(6토큰), 스프레드 5.5%, 같은 임대 ik tg96 82.74 ± 0.31 → 잔여 1.075배.**

## 세 번 연속으로 "큰 것"이 작았다

이 구간의 기록할 만한 것은 숫자보다 그 패턴이다.

**perf는 `quantize_col`이 메인 스레드의 15.5%라고 했다.** 스칼라 인코더였고 메인 스레드는 임계 경로이니 2 ms짜리로 읽었다. AVX2로 바꾼 값은 +0.9%. 위임 라운드 자체는 좋았다 — 스펙이 "반올림은 `_mm256_cvtps_epi32`와 같다"고 적은 전제를 고쳐 잡았다(amax가 비정규 수준이면 스케일이 inf로 넘치고, 거기서 포화 변환과 스칼라의 가수 트릭이 갈린다; 그래서 가수 트릭을 레인 단위로 그대로 돈다). FAIL-first 둘(마지막-최대 선택, 절삭)도 실제 실패 단언을 인용해 왔고, 스칼라 오라클 본체는 해시로 대조해 한 바이트도 안 바뀐 것을 확인했다.

**풀 벤치는 빈 디스패치가 4.56 µs라고 했다.** 원인 둘을 찾았다: 대기자가 없어도 매 디스패치 `notify_all`(futex 시스템 콜 — 메인 스레드 프로파일의 `syscall` 1.6%가 이것), 그리고 워커 31개가 한 캐시 줄의 `remaining`을 차례로 감소시키는 소유권 이전 사슬. 고치니 풀 벤치는 **4.56 → 1.61 µs**다. 디코드는 77.49 → 77.55. 빈 클로저에서는 워커 31개가 동시에 끝나서 그 사슬이 생기지만 실제 스텝에서는 끝나는 시각이 흩어져 있어 처음부터 없던 비용이었다. 풀 벤치의 µs는 스텝의 µs가 아니다.

**레벨2 프로파일은 가장 느린 청크가 평균보다 20–40% 길다고 했다.** 디스패치 하나의 벽시간(span)과 그 안에서 가장 오래 걸린 청크(slowest)를 프로파일 열로 추가하고 본 값이다: batch Q3_K가 slowest 338 ms 대 dot/32 241 ms. 스텝당 2.2 ms의 스큐 — ik와의 격차 전부보다 크다. 청크 인덱스별 분포는 ±2%로 평평했으므로 기계가 아니라 디스패치마다의 잡음이고, 그러면 답은 가중 분할이 아니라 꼬리 훔치기다. 구현했다: 레인마다 커서 하나, 주인은 자기 레인을 앞에서부터 블록 단위로 가져가고 끝난 참가자는 남의 레인 앞 블록을 가져간다. 디코드는 안 움직였다.

그제야 계측기를 의심했다. 레벨2는 행마다 `Instant::now()`를 두 번 부르고, Q3_K 행 하나의 내적이 수백 ns다. 행별 타이머가 없는 레벨1에서 같은 열을 다시 재면(스텝당):

| | 훔치기 끔 | 켬 |
|---|---:|---:|
| 평균 청크 바쁜 시간 | 9.28 ms | 9.54 |
| 가장 느린 청크 | 10.34 | 10.14 |
| 디스패치 span | 10.93 | 10.80 |

스큐는 40%가 아니라 **11%(1.06 ms)**, 장벽 자체는 0.58 ms다. 훔치기가 span에서 걷어낸 것은 0.13 ms이고 A/B의 무차이와 맞는다. 프리필에서는 청크가 길어 같은 장치가 +25%다 — 그래서 넣었다. `BLOOMERY_STEAL=0`이 레버다.

## 그래서 지금의 산수

레벨1 기준 스텝 13.9 ms(프로파일 세금 포함): 행 디스패치의 **평균 청크 9.3 ms** + 스큐 1.06 + 장벽 0.58 + 나머지 3.0. ik는 12.1 ms × 이용률 0.75 = 9.1 ms의 커널 시간에 3.0 ms의 나머지다. 계산 바닥은 같고(9.3 대 9.1), 남은 0.9 ms는 전부 "나머지"에 얇게 퍼져 있다: matmul 앞뒤(사이트 벽시간 − span) 1.09 ms, q_nope2 0.45, flash 0.34, swiglu 0.22, wv_b_heads 0.18, rms_norm 0.12, MoE 부기 0.23. 단일 항목으로 1 ms짜리는 더 없다.

남은 구조적 지렛대는 디스패치 수다. 디스패치 하나가 장벽 1.5 µs + 스큐 2.8 µs를 내므로 층당 4개를 묶는 이종 묶음 디스패치(`docs/cpu-dispatch-plan.md` 3단계)가 0.5 ms 안팎이다. 그것과 "나머지"의 잔돈을 합쳐야 같은 선이다.

## 규약으로 남긴 것

레벨2의 절대값은 원래도 "비율만 믿으라"는 경고가 붙어 있었다. 이번에 틀린 것은 비율이었다 — 타이머 세금은 행 수에 비례하므로 청크의 *길이 분포*를 부풀린다. span·slowest·청크별 분포는 레벨1에서 찍히게 했고, 스큐는 레벨1에서만 읽는다.
