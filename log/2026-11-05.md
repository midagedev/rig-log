## Spark 를 V4.1 의 expert tier 노드로 — 첫 bind 가 가르쳐 준 세 가지 (sparkr3)

TCP 와이어와 count word 가 main 에 오른 뒤(bloomery 1ace3447c) Spark 의 tier_server(r3node 트리, sm_121a 네이티브 빌드,
`--features deepseek41`)에 워크스테이션의 stage 를 `--place bp` 로 붙였다(`BLOOMERY_TIER_NODES`, `BLOOMERY_TIER_LINK=tcp`,
`BLOOMERY_PREFILL=steps`). 재지 못한 것: a. 대신 세 가지가 나왔다.

1. **플랜은 Spark 의 census 를 카드 스펙으로 받아 tier 를 125.8 GB(7,499 experts)로 잡는다.** 통합 메모리 121 GiB 의 거의 전부다.
   첫 open 은 모델 복사 직후 page cache 가 찬 상태라 커널 OOM(NVRM NV_ERR_NO_MEMORY)으로 죽었고, cache 를 비운 두 번째는
   791 MB 를 남기고 올라왔다. Spark 는 공유 기계라(docker 컨테이너가 20–45 GB 를 쓴다) 노드의 room 은 total 이 아니라
   free 에서 파일 읽기 페이지와 다른 세입자를 뺀 값이어야 한다. `BLOOMERY_CARD_BUDGET` 은 노드가 있으면 한 값만 받아 A6000 의
   몫까지 깎는다 — 노드별 표기가 필요하다(placement, ~20줄).
2. **프롬프트 배치는 노드 tier 를 거부한다**(`feed the prompt as steps`). 지금 코드로 Spark 는 디코드에만 기여한다.
3. **Spark 의 드라이버 580.178.04 는 CU_STREAM_MEM_OP_ATOMIC_REDUCTION 을 "invalid argument" 로 거부한다.** 첫 스텝의
   tier go(`[wait_geq, add u32::MAX]`)가 노드 스트림에서 죽었다. 드라이버 API 탐침(CUDA 13.3 cuda.h 로 양쪽에서 빌드):

   | 메모리 | wait32 | write32 | batch(wait, write) | batch(atomic add) |
   |---|---|---|---|---|
   | GB10 580.178.04: cuMemHostAlloc(DEVICEMAP) | ok | ok | ok | invalid argument |
   | GB10: cuMemHostRegister(DEVICEMAP) | ok | ok | ok | invalid argument |
   | GB10: cuMemAlloc | ok | ok | ok | invalid argument |
   | GB10: managed | invalid argument | – | – | – |
   | A6000 615.71.09: 위 셋 | ok | ok | ok | ok |
   | A6000: managed | invalid argument | – | – | – |

   apt 에 더 새 드라이버는 없다. 펌프는 세대(generation)로 done 을 읽으니 상수 write 로 대신할 수 없다. 엔진 쪽 수정은
   add 를 system-scope atomic 커널 한 런치로 대신하고(층당 go 하나·done 하나, ≈ 2·c_node), 어느 쪽을 쓸지는 버전이 아니라
   컨텍스트 open 때의 탐침으로 정한다 — 라운드 r3b.

Claude(Fable 5.1)가 탐침과 실행을 맡았고, 표와 해석은 사람이 읽고 확인했다.

## 호스트 룸을 190 GB 로 묶은 ws 단독(NVMe 페이징) 대 ws+Spark — 1.3 배, warm 에선 parity (sparkroom)

"박스가 못 담는 모델을 Spark 가 담는다" 를 지금 파일로 흉내 낸 사이팅. 두 arm 모두 `BLOOMERY_HOST_ROOM=190G`, 단독 arm 은
`--place a` 에 `BLOOMERY_NVTIER_BYTES=90G`(와 `BLOOMERY_R8=off`: NVMe 티어는 r8 사이드카 아래의 paged plan 을 이름으로 거부한다),
노드 arm 은 `--place bp` + Spark 티어(tcp, `BLOOMERY_CARD_BUDGET=90G`, `BLOOMERY_HOST_LOCK=1`). main 9a3d3b519 한 바이너리,
한 lease, 4 라운드, prose P 512 n 96, A6000 스테이지. 카드 `docs/cards/sparkroom-decode.card` 예측: 단독 13 미만, 노드 25..40.

| arm | tok/s(p50) | warm step (last10 p50) | pp tok/s | majflt |
|---|---|---|---|---|
| ws 단독, 190 GB 룸, NVMe 티어 | 27.5–28.5 | 25.3–25.7 ms (≈ 39) | 22–32 | 1.9–4.9k |
| ws + Spark, 같은 룸 | 35.2–37.2 | 26.3–27.0 ms (≈ 37) | 60–73 | 68–94k |

예측이 빗나간 항은 NVMe 에 실제로 남는 바이트다. `BLOOMERY_NVTIER_BYTES` 는 NVMe 쪽이 아니라 **RAM arena** 를 정한다
(레지스트리 행: "the RAM arena the NVMe expert tier fills"): plan 줄 `paged=124 GB arena=96.6 GB` 라 호스트 90 + arena 96.6 =
186.5 GB 가 RAM 에 있고 NVMe 에서 도는 전문가는 27.4 GB 뿐이다. 그 27.4 GB 가 warm step 에 +6 ms (19.4 → 25.5) 를 냈으니
NVMe 항은 ≈ 0.22 ms/GB-short [derived, 한 점]. 노드 arm 은 nodebatch 와 같은 37 — 노드 왕복 7 ms 그대로다. 그래서 p50 으로는
1.3 배(단독 arm 의 첫 스텝들이 느리다), warm 으로는 단독 페이징이 근소하게 빠르다. 395 GB 파일(UD-IQ3_XXS, RAM 밖 ≈ 87 GB)
은 같은 항으로 단독 ≈ 21 tok/s 대 +Spark ≈ 31 [derived, `spark-model.py decode_bigger_quant`] — 그 파일이 내려오면 잰다.

## plan (a) 의 P 512 prefill 은 한 pass 라 겹치지 않는다 — pass 수를 늘리면 220 → 311 → 354 (prefill-passes)

같은 바이너리, 같은 lease, plan (a), 2 라운드 (카드 `docs/cards/prefill-passes.card`, 예측 P 1024 = 270..320):

| P | passes | pp tok/s |
|---|---|---|
| 512 | 1 | 210, 221 |
| 1024 | 2 | 311 (다른 한 행 209, 원인 미상, cpu-busy·cold 표시 없음) |
| 2048 | 4 | 350, 358 |

프롬프트는 `T_MAX = 512` 위치마다 한 pass 로 잘리고(`prefill.rs:141`), `BLOOMERY_PREFILL_GROUP`(기본 2)은 pass 들을 레이어
단위로 겹친다(이전 pass 의 host serve 위에 다음 pass 의 카드 route). P 512 는 pass 가 하나라 카드 ~36 ms 와 호스트 ~29 ms 가
레이어마다 직렬이다 — 58 ms = 220. 모델 `prefill_passes`(pass 당 ~29 ms + 드러난 host leg 하나): 1024 → 295, 2048 → 354,
4096 → 393 (어제 416–427 측정). 그러니 P 512 를 256 × 2 로 자르면 ≈ 295, 128 × 4 면 ≈ 354 [derived] — Spark 없이 박스
단독의 헤드라인이 +35..60 % 다. 자르는 레버(`BLOOMERY_PREFILL_CUT`)를 짓는 라운드(prefillcut)를 열었다; 같은 바이너리 A/B
로 잰다.

같은 계산을 노드에 대면: 겹침이 켜진 깊이에서 레이어-pass 의 카드 항이 ~29 ms 라, 노드가 자기 전문가를 계산해 돌려주는
leg(bf16 로 합산해 돌려줘도 ≈ 32 ms: 링크 왕복 9 + GB10 읽기·GEMM 16 + pack 7)는 parity 다. 노드의 prefill 자리는 호스트
leg 가 bound 일 때뿐이고, 지금 Q3_K_M(호스트 set 90 GB) 은 카드가 bound 다. 395 GB 파일은 호스트 set 이 ~160 GB 로 커져
호스트 leg ≈ 51 ms 가 bound 가 되고, 노드가 95 GB 를 가져가면 ≈ 32 ms: +50 % [derived]. 즉 Spark 의 이득은 decode 도 prefill
도 "박스가 못 담는 파일" 한 곳에 모인다.

## P 512 프롬프트를 둘로 자르면 pp 217 → 281, 그런데 그 뒤의 decode 가 −14 % (prefillcut)

`BLOOMERY_PREFILL_CUT`(prefillcut 라운드, Sonnet 5.5: 한 pass 가 담는 위치 수, 기본 512 = 오늘 그대로, `batches()` 의 한
소유자 `BodyLevers::batches`, 0·513 은 이름으로 거부, 비트 불변을 prefill 게이트가 256 에서도 확인). 같은 바이너리·lease,
plan (a), A6000, prose P 512 (카드 `docs/cards/prefillcut-ab.card`, 예측 265..310):

| cut | passes | pp tok/s (2 라운드) | decode p50 (n 96) | warm step |
|---|---|---|---|---|
| 512 | 1 | 215, 219 | 45.8, 46.4 | 18.9 ms |
| **256** | 2 | **280, 282** | 39.4, 40.1 | 20.5–21.3 ms |
| 128 | 4 | 208, 208 | 37.6, 38.4 | 21.1–21.3 ms |

pp 는 모델대로(+29 %), 128 은 라운드의 종이 분해가 예고한 호스트 union 의 전문가당 바닥(W ≈ 126 µs, 열 9 개 아래선 더
안 줄어든다)에 먹혔다. 예상 밖은 decode: n 512 로 늘려도(`prefillcut-decode.card`, 예측 last10 18.5..19.8) 256 arm 의
last10 20.4 ms 대 19.4–19.8, p50 41 대 46 — 과도현상이 아니라 정상상태다. 단서는 `residency pass pass=prompt` 의
`stage_us`: 한 pass 2.0–2.3 s, 두 pass 0.26–0.40 s. residency 가 프롬프트 호출 밑에서 올리는 hot set 이 ~6 배 작게 올라가고
decode 가 그 set 으로 시작한다. admission floor(STREAM_FLOOR × members = 64 → 행 비례 32)를 고쳐 봤지만 stage_us 0.38–0.40,
decode 39.7–39.9 로 그대로(카드 `prefillcut-floor.card`, 되돌림) — 원인은 floor 가 아니다. 레버는 opt-in 으로 랜딩하고
"cut 아래의 residency pick" 은 triage 항목.

## Spark 가 자기 전문가 블록을 직접 계산하는 prefill — 폴트 0, pp 48–69 → 114–127, 그래도 ws 단독의 절반 (nodeprefill)

nodeprefill 라운드(Opus 5.5): wire 프로토콜 9 (`BlockOpen`, `Block` 에 q8_1 plane 과 place, 회신은 노드 slot 의 f32 행,
레이어당 한 프레임씩), 노드가 `Ds41Tier::enqueue_block` 을 돌리고, `BatchSlots` 뷰는 더 이상 노드 전문가를 HOST 로 읽지
않는다. loopback 노드로 토큰·logit 이 로컬 tier 카드와 bit 단위로 같다(B9 exact, FAIL-first 와 변이체 둘 다 빨강).
Spark 로 잰 값(카드 `nodeprefill-pp.card`, 예측 125..165; 노드 arm `--place bp` + Spark tcp, 2 라운드):

| arm | pp tok/s | decode p50 | majflt | union_tier_slots / off-card |
|---|---|---|---|---|
| plan (a) | 219 (r2 는 96k 폴트의 cold 행 58, 버림) | 46.6 | 0 | — |
| ws + Spark, 노드가 블록 계산 | 127, 114 | 37.7, 38.4 | 4, 0 | 40,367 / 63,194 |

라운드의 종이 분해(노드 leg 57.7 ms = 요청 3.1 + GB10 16 + pack 3.5 + 회신 39 MB 31.6 + landing 3.5, P 512 는 한 pass 라
카드 ~29 ms 와 직렬 → 147)보다 조금 낮다 — decide-below: 회신 39 MB/레이어가 1.24 GB/s 를 못 채우거나 landing 루프가
복사로 안 컴파일됐다(라운드의 watch item). 노드에서 합산해 bf16 으로 돌려줘도 ~207 [derived] 이라 ws 단독 219 과 cut 256
의 281 을 못 넘는다. 오늘의 결론: **10GbE TCP 노드로는 decode·prefill·용량 셋 다 박스 단독을 못 넘는다**; 남은 레버는
멀티 스트림(노드 요청이 행별이라 행 묶음 wire 가 먼저)뿐.

## 정정: cut 256 의 pp +29 % 는 residency 가 덜 올린 값이었다 — 같은 admission 이면 pp +1.5 %, decode 동률 (prefillcut, 둘째 읽기)

원인(residency-cut-map, 읽기 전용): pick 은 그룹의 **첫 멤버 배치의 count 만** 보고(`prefill.rs` 의 picked 비트셋, 둘째 배치의
id 는 세지 않는다), floor 는 STREAM_FLOOR × 멤버 수. 2 × 256 은 "256행 count 대 floor 64", 1 × 512 는 "512행 count 대 32"
라 4 배 엄격했다. 엔진에 있는 `call_pick_routed_scaled`(첫 멤버의 count 를 scale 배로 친다)로 count 를 T_MAX / 행 = 2 배,
floor 를 행 비례(32)로 두면 2 × 256 이 1 × 512 조건이 된다. 같은 카드(`prefillcut-floor.card`, 예측 last10 18.8..20.0), n 512,
2 라운드:

| arm | pp tok/s | decode p50 | last10 step | stage_us |
|---|---|---|---|---|
| cut 512 | 219, 220 | 46.6, 46.7 | 19.1 ms | 2.24–2.28 s |
| cut 256, 그룹을 T_MAX 행 단위로 가격 | 222, 223 | 46.2, 46.2 | 18.7–18.9 ms | 2.27 s |

decode 는 수렴했고(예측 안), pp 는 280 에서 222 로 돌아왔다. 즉 **280 은 staging 을 1/6 만 한 프롬프트의 값**이었다. residency
가 프롬프트 호출 밑에서 ~40 GB(churn_bytes) 를 host 세그먼트로 복사하는 일은 한 pass 에선 카드 항(호스트가 노는 ~29 ms/레이어)
밑에 숨고, pass 를 겹쳐 호스트를 꽉 채우면 그 복사가 DRAM 대역폭(119 GB/s, 40 GB ≈ 0.35–0.5 s)에서 드러난다 [derived]. P 512
의 prefill 은 카드 직렬 + staging 바이트로 묶여 있고, cut 은 residency 를 켠 조건에서 ~0 이다. 레버는 opt-in(기본 512, 비트
불변)으로 랜딩하고 그룹 가격 수정(기본 1 × 512 와 2 × 512 에선 값이 같다)을 같이 싣는다. 헤드라인은 없다.

Claude(Fable 5.1)가 라운드를 지휘하고 사이팅을 돌리고 표를 썼다; 해석은 사람이 읽고 확인했다.

## 호스트 룸 128 GB 에선 ws 단독이 decode 19·pp 29, 같은 룸에 Spark 를 붙이면 35·106 — decode 1.8 배, prefill 3.6 배 (smallroom)

sparkroom(룸 190G)은 arena 너머 24 GB 라 1.3 배에 그쳤다. 비용 모델의 NVMe 항 두 가지(선형 0.22 ms/GB 와
핫비율 항)가 룸 128G 에서 3 배 갈려서, 그 지점을 재는 사이팅을 열었다(카드 `docs/cards/smallroom-decode.card`,
bloomery train 트리 540ad8c61 의 코드 + 카드 파일, 박스의 `generate_ds41` 과 Spark 의 `tier_server` 를 같은 트리에서
빌드). 조건: V4.1-Flash Q3_K_M, A6000 stage, prose P 512, depth 512, n 96, 3 라운드, 각 arm 자기 프로세스에서 로드,
plain arm `--place a` + `BLOOMERY_HOST_ROOM=128G|160G` + `BLOOMERY_NVTIER_BYTES=60G|80G` + `BLOOMERY_R8=off`(읽기는 기본값
`O_DIRECT` 라 페이지 캐시가 돕지 않는다), 노드 arm `--place bp` + Spark 티어(tcp) + `BLOOMERY_CARD_BUDGET=110G` +
`BLOOMERY_HOST_LOCK=1`, 매 open 전 Spark 의 캐시 드롭. 플랜 줄: 룸 128G plain 은 카드 45 GB · 호스트 고정 55.5 GB ·
페이지 대상 158 GB 중 arena 64 GB(디스크 너머 94 GB); 룸 160G 는 arena 86 GB(62 GB); 노드 arm 은 두 룸 다 호스트 97.7 GB ·
노드 티어 ~116 GB · paged 0.

| arm | decode tok/s(p50) | p50 ms | pp tok/s (P 512) |
|---|---|---|---|
| 룸 128G 단독, NVMe 티어 | 19.35–19.61 | 51.0–51.7 | 28.8–29.2 |
| 룸 128G + Spark | 34.69, 35.04 | 28.5–28.8 | 104.5–108.2 |
| 룸 160G 단독, NVMe 티어 | 25.23–25.65 | 39.0–39.6 | 29.1–30.3 |
| 룸 160G + Spark | 34.57, 34.76 | 28.8–28.9 | 106.2 |
| (참고) 박스 256 GB 단독, plan a, 11-05 앞선 사이팅 | ~37 | ~27 | 210–221 |

읽기: ① decode 의 NVMe 항은 선형으로 남는다 — (51.2 − 27) / 94 = 0.26 ms/GB, (39.4 − 27) / 62 = 0.20 ms/GB, sparkroom 의
0.22 와 한 줄에 선다. 핫비율 항(7–13 예측)은 기각. ② 무너지는 건 prefill 이다: 단독 arm 의 prompt 17.7 s 는 페이지 대상
158 GB 를 한 번 읽는 시간(≈ 9 GB/s)과 맞는다 — P 512 가 거의 모든 전문가를 건드리니 프롬프트마다 디스크를 통째로 읽는다.
③ 노드 arm 은 예측 35–38 의 아래 끝에서 1–2 % 빠졌다(34.3–35.0): 노드 지분이 sparkroom 의 95 GB 에서 116 GB 로 커진 만큼
노드가 스텝마다 더 읽는다 [derived]. ④ 노드 arm 6 회 중 2 회(r2 160G, r3 128G)가 Spark 쪽 open 거부
(`cuDevicePrimaryCtxRetain: out of memory`)로 FAIL 행이 됐다. tier_server 는 로드를 닫은 뒤에도 RSS 113 GB 를 쥔 채 다시
listen 하고(`node 0 closed the load` 다음 `listening on`), 이번 티어 116 GB 가 Spark 의 121 GB 에 바짝 붙어 둘째 open 이
튕긴 것으로 읽는다. 남은 4 행이 서로 1 % 안이라 표는 선다; 닫을 때의 해제(또는 이름 있는 사전 거부)는 triage 항목.

결론: "128 GB 워크스테이션 + DGX Spark 한 대" 가 정직한 헤드라인이다 — 같은 룸에서 decode 1.8 배, prefill 3.6 배, 그리고
256 GB 박스 단독의 decode 에 5 % 안으로 붙는다. 룸 캡은 RAM 만 흉내내고 CPU 코어 수(박스 64)는 그대로라는 조건이 붙는다.
더 작은 룸은 부족분이 노드 티어 상한(125.8 GB)을 넘어 Spark 로도 안 된다. 다른 큰 MoE(Mistral-Large-4 1T-A52B, Muse-Spark
816B-A42B)는 모델상 이득이 더 작다 — 노드 항이 활성 바이트에 비례하고 왕복은 고정이라 A22B 가 가장 유리하다 [derived,
`tools/spark-model.py decode_other_model`].

테이프(클립용, 카드 `docs/cards/smallroom-tape.card`, 같은 트리, `bloomery-serve-ds41 --ctx 32768` 을 sitting 과 같은 플랜으로 띄워
`toktape record`(greedy, 256 토큰, 프롬프트 캐시 끔, 워밍업 1회 뒤 기록 1회), 한국어 질문 51 토큰): 룸 128G 단독 20.9 tok/s ·
ttft 2.13 s(pp 24) / 룸 128G + Spark 35.5 tok/s · ttft 0.60 s(pp 86). 둘 다 카드의 예측 안(단독 18..21, 노드 34..37); 짧은
프롬프트라 pp 는 P 512 행보다 낮게 읽힌다. 첫 Spark 테이프는 워밍업의 프롬프트 캐시 적중(prompt_n 1, ttft 39 ms)이라 버리고
캐시를 끄고 다시 찍었다; 그 사이 노드 open 거부(OOM)가 한 번 더 났다(위 ④).
