## 프롬프트 경로의 병목, 오늘의 main 에서 다시 읽음

Spark 노드가 프롬프트 블록을 받는 설계(r4prompt)는 9월 29일의 S0 측정(plan a, prose P512: 호스트 union 45.72 ms, card_in 11.53 ms 한 층-배치)을 근거로 "프롬프트는 호스트 union 이 묶는다, 노드가 그 시간을 덜어 pp512 +5…+8 %"를 유도했다. 그 근거가 오늘도 참인지, 그리고 P4096 행의 분모(S0 의 union 44.19 × 320 이 체인 10.88 s 보다 커서 맞지 않던 것)가 무엇인지를 한 임대로 읽었다: A6000, main f83a69dea, `BLOOMERY_STEP_STATS=1 just depth-gpu-ds41 prose:512 prose:4096`, 카드 `docs/cards/sparkr4-union.card`(예측 43.4..48.0).

| 팔 [provisional: 증인이 cpu-busy] | pp tok/s | 서비스된 층-배치 | union 평균 ms | card_in 평균 | wait 평균 |
|---|---|---|---|---|---|
| prose 512 (예열) | 213.89 | 40 | 28.94 | 36.25 | 0.00 |
| prose 512 | 219.77 | 40 | 28.79 | 36.13 | 0.00 |
| prose 4096 | 416.08 | 220 | 30.93 | 16.56 | 1.47 |
| prose 512, 2차 사이팅 [cold: 파일 미예열; cpu-busy 0/2] | 209.45 | 40 | 29.81 | 37.53 | 0.00 |
| prose 4096, 2차 사이팅 [cold] | 427.17 | 220 | 30.42 | 15.95 | 1.44 |

2차 사이팅(04:05, main 9b20c5134, cpu-busy 행 0)이 같은 체제를 5 % 안에서 확인했다(cold 표시는 majflt, 파일이 예열되지 않았다). 예측 밖, 아래다. 9월 29일 이후 호스트 union 이 45.7 에서 28.8 ms 로 내려왔고(어느 변경이 옮겼는지는 재지 않았다), 카드 쪽은 11.5 에서 36 ms 로 올라 P512 는 지금 카드가 묶는다(wait 0). 그래서 노드가 union 을 줄여도 P512 벽은 움직이지 않는다 — v1 노드 leg 28–30 ms 는 카드 36 ms 아래 숨지만 이득은 0 에 가깝다. 반대로 P4096 은 union 30.9 > card_in 16.6 으로 union 이 묶고, 분모는 320 이 아니라 220 이다(30.9 × 220 = 6.8 s, 프롬프트 9.84 s 의 69 %). 노드의 프롬프트 이득은 긴 프롬프트에 있고, 거기서도 v1 leg 는 union 과 거의 같아 q8 go 와 파이프라인 reply(leg ~15 ms)가 있어야 한다. 증인: 다른 원격 디렉토리의 빌드가 코어 하나를 58–99 % 썼다(32 코어 중 하나) — 카드의 조건(cpu-busy 없음)을 어겼으므로 행은 잠정값이고, 방향(card_in 세 배, union 하락)은 빌드 하나로 생기지 않으니 판정은 유지하되 카드 B 전에 조용한 기계에서 한 번 더 읽는다; 다른 카드의 compute 프로세스 0.

틀렸던 것: 두 달 된 앵커를 모델 입력으로 쓴 것. 프롬프트 경로는 그 사이 두 번 바뀌었다. 다음은 r4prompt 1.5 를 이 행으로 다시 세우고, A/B 카드 B 는 P4096 만 연다.

## Spark 를 V4.1 의 expert tier 노드로 — 첫 bind 가 가르쳐 준 세 가지 (sparkr3)

TCP 와이어와 count word 가 main 에 오른 뒤(bloomery 1ace3447c) Spark 의 tier_server(r3node 트리, sm_121a 네이티브 빌드,
`--features deepseek41`)에 워크스테이션의 stage 를 `--place bp` 로 붙였다(`BLOOMERY_TIER_NODES`, `BLOOMERY_TIER_LINK=tcp`,
`BLOOMERY_PREFILL=steps`). 재지 못한 것: a. 대신 세 가지가 나왔다.

1. **플랜은 Spark 의 census 를 카드 스펙으로 받아 tier 를 125.8 GB(7,499 experts)로 잡는다.** 통합 메모리 121 GiB 의 거의 전부다.
   첫 open 은 모델 복사 직후 page cache 가 찬 상태라 커널 OOM(NVRM NV_ERR_NO_MEMORY)으로 죽었고, cache 를 비운 두 번째는
   791 MB 를 남기고 올라왔다. Spark 는 공유 기계라(docker 컨테이너가 20–45 GB 를 쓴다) 노드의 room 은 total 이 아니라
   free 에서 파일 읽기 페이지와 다른 세입자를 뺀 값이어야 한다. `BLOOMERY_CARD_BUDGET` 은 노드가 있으면 한 값만 받아 A6000 의
   몫까지 깎는다 — 노드별 표기가 필요하다(placement, ~20줄).
2. **프롬프트 배치는 노드 tier 를 거부한다**(`feed the prompt as steps`). 지금 코드로 Spark 는 디코드에만 기여한다.
3. **Spark 의 드라이버 580.178.04 는 CU_STREAM_MEM_OP_ATOMIC_REDUCTION 을 "invalid argument" 로 거부한다.** 첫 스텝의
   tier go(`[wait_geq, add u32::MAX]`)가 노드 스트림에서 죽었다. 드라이버 API 탐침(CUDA 13.3 cuda.h 로 양쪽에서 빌드):

   | 메모리 | wait32 | write32 | batch(wait, write) | batch(atomic add) |
   |---|---|---|---|---|
   | GB10 580.178.04: cuMemHostAlloc(DEVICEMAP) | ok | ok | ok | invalid argument |
   | GB10: cuMemHostRegister(DEVICEMAP) | ok | ok | ok | invalid argument |
   | GB10: cuMemAlloc | ok | ok | ok | invalid argument |
   | GB10: managed | invalid argument | – | – | – |
   | A6000 615.71.09: 위 셋 | ok | ok | ok | ok |
   | A6000: managed | invalid argument | – | – | – |

   apt 에 더 새 드라이버는 없다. 펌프는 세대(generation)로 done 을 읽으니 상수 write 로 대신할 수 없다. 엔진 쪽 수정은
   add 를 system-scope atomic 커널 한 런치로 대신하고(층당 go 하나·done 하나, ≈ 2·c_node), 어느 쪽을 쓸지는 버전이 아니라
   컨텍스트 open 때의 탐침으로 정한다 — 라운드 r3b.

Claude(Fable 5.1)가 탐침과 실행을 맡았고, 표와 해석은 사람이 읽고 확인했다.

## ws+Spark 의 첫 디코드 숫자 — 노드가 residency-off 스테이지를 +17 % 돕지만, 노드 길은 residency 를 끈다 (sparkr3-ab)

   Spark 를 비우고(118 GB free) r3b 트리(커널 word add, 2d225452c)로 같은 임대 A/B: `just depth-gpu-ds41 prose:512@place=a
   prose:512@place=bp,BLOOMERY_TIER_NODES=…,BLOOMERY_TIER_LINK=tcp`, `BLOOMERY_CARD_BUDGET=90G BLOOMERY_PREFILL=steps`,
   4 라운드, n 96, depth 512, 스테이지 A6000. 노드 tier = 5,643 experts / 94.65 GB on GB10, `word_ops=kernel`.
   카드 `docs/cards/sparkr3-ab.card` 예측 +2.8..+9.6 %.

   | 라운드 | ws 단독 plan a, tok/s(p50) | bp + Spark 노드, tok/s(p50) |
   |---|---|---|
   | r1 | 29.16 (majflt 2) | 33.08 |
   | r2 | 27.25 (cold, majflt 117k) | 33.69 |
   | r3 | 27.90 (cold, majflt 94k) | 31.81 |
   | r4 | 28.17 (cold) | 33.16 |
   | 평균 | 28.1 | 32.9 (**+17 %**) |

   [provisional] 러너가 노드 팔 행을 FAIL 로 적었다(두 카드 표 규칙: 둘째 카드가 3090 이어야 하는데 GB10) — 런은 rc 0,
   96 토큰, 숫자는 팔 로그의 SMOKE 행. 러너 수정은 라운드 runner-node. ws 단독 r2–r4 는 노드 팔의 로드가 페이지 캐시를
   밀어내 cold(다음 사이팅은 `BLOOMERY_AB_ORDER=blocks`).

   카드가 빗나간 항은 노드 몫: 카드는 41 GB(공유 Spark 의 free 에 맞춘 첫 스모크)로 a 를 잡았고, 사이팅은 94.65 GB 를
   받아 호스트 leg 가 그만큼 더 줄었다. 다음 카드는 노드 몫을 `tier_bytes` 로 쓴다.

   **구조적 사실.** 노드 tier 는 프롬프트 배치를 거부하고(`feed the prompt as steps`), `BLOOMERY_PREFILL=steps` 는 residency
   를 끈다(`residency lever residency=off why=prefill_steps`). 그래서 이 A/B 의 양쪽은 residency off 이고, ws 단독의 최고치
   (plan a, 배치 프리필, residency mid)는 같은 사이팅 조건에서 46.0 tok/s(11-05 04:05, n 96 d512) 다. ws+Spark 가 그걸
   넘으려면 노드가 있어도 프롬프트 배치가 돌아야(호스트가 노드 experts 를 배치에서 대신 서빙) residency 가 돌아온다. 프리필도
   같다: 노드 팔 pp 24–33 tok/s(steps) 대 plan a 배치 ~220.

   Spark 쪽 운영 사실: GB10 의 컨텍스트 할당(`cuDevicePrimaryCtxRetain`)은 페이지 캐시를 회수하지 않는다 — 노드 로드가 남긴
   88 GB 캐시 위에서 다음 open 이 `out of memory`. 매 open 전 `echo 3 > /proc/sys/vm/drop_caches`.

Claude(Fable 5.1)가 사이팅을 돌리고 표를 썼고, 해석은 사람이 읽고 확인했다.
