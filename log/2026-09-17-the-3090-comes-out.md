# The 3090 comes out: a second hang, a sale check cut at 99.9 %, and a lease nobody held

**2026-09-17, 06:28–07:23.** The 24 GB card left the machine this morning.
This entry records why, what its last test said, and what the test could not
say because the power went off ten seconds before it finished.

## The second hang (2026-09-16, 21:56:59)

The card had already fallen over once that day, at 00:01 under a two-process
DDP training run. The second time it was serving Qwen3.6-35B-A3B whole
(`configs/qwen36-3090-serve.sh`, 22.3 GB) for the Telegram agent when a
second process — the agent itself, running torch/diffusers directly with no
`CUDA_VISIBLE_DEVICES`, so device 0 was the 3090 — initialised CUDA on the
same card. The server logged `unspecified launch failure`; the kernel then
logged GSP RPC failures (`rpcSendMessage failed 0xf`); there was no Xid line,
no AER line, and the link registers under `41:00.0` and its root port
`40:01.1` read clean (`UESta`/`CESta` all `-`). `nvidia-smi -r` failed; only a
power cycle brought the card back. Both hangs share two facts: sustained
memory-bandwidth-heavy load, and a second CUDA context arriving on the card.

That fingerprint is not a slot fingerprint. The A6000's move on 09-16 fixed a
card that was logging Gen4 correctable errors (27 in 483 s of load, 0 at Gen3,
0 after the move). The 3090 logged none before either hang, so the question
"would another slot help" was answered from the record: nothing in it says
so. The user chose to remove and sell the card instead of testing further; a
web-research round on the GSP-failure symptom class was started for the sale
disclosure and is reported separately when it lands. Reproduction attempts
are off the table with the card out.

## The sale check, and where it stopped

`tools/gpu-sale-check.sh` ran against the 3090 alone (UUID-pinned, the
A6000 untouched, lease held, 1 Hz witness) from 06:28:38:

| step | result |
|---|---|
| cuda_memtest, 3 passes over 24 GB | rc 0, 27 s, **0 memory errors** |
| gpu_burn, 30 min, results compared against a reference | reached **99.9 %** (42 968 iterations, 26.2 TFLOP/s fp32) with **0 errors**, then the machine was powered off at 06:59:26 — no final `OK`/`FAULTY` line |
| witness over 1 842 s | power max/mean 421 / 415 W, SM clock min/mean 210 / 1 613 MHz, GPU temperature max **77 °C**; throttle reasons seen 0x1, 0x4, 0x400, 0x600 |
| kernel log during the run (previous boot's journal, 06:28:38 → shutdown) | 3 lines, all the shutdown itself; **no Xid, NVRM or AER** |
| PCIe registers after the run | not taken — the run was interrupted |
| torch PCIe bandwidth and fp16 matmul | not run — same reason |

The power-off was the user's, to pull the card; the runner wrote
`INTERRUPTED` and released the lease. The buyer's sheet
(`tools/gpu-check-sheet.py`) now renders an interrupted run honestly: the
gpu_burn cell says at what percentage it stopped and why, missing files read
as "not run", and the AER block says it is the start-of-run snapshot. The
report counts the burn as a pass only when it was cut after 99 % with zero
errors, which this one was.

The runner's own summary line said `errors reported: 1` after the memtest.
That was the counter, not the memory: cuda_memtest prints
`serial=unknown (NVML runtime error)` on GeForce cards and the grep for
`error|fail` caught it. Fixed in the runner and the sheet, with the line
excluded by name. **Struck**: the `errors reported: 1` in `run.log` of
`sale-3090-1`.

## A lease that nobody held

A peer session's overnight job reported that it waited from 00:00 to 02:00 on
a held `/home/user/gpu-lease` with both cards at 1 MiB, and trained nothing.
The holder was this repo's smoke run from 22:44:56 the evening before: a new
copy of the runner was `scp`'d over the script while bash was still reading
it, bash stopped on a syntax error at a line it had not reached, the EXIT
trap never ran, and the lease and witness stayed until 06:27. The runner now
execs from a private copy (commit `4e26ef7`), and the lease rule gained the
reader's half: the file carries the holder's pid, and a lease whose pid does
not answer `kill -0` is no lease. Details and the measured field order are in
[`docs/quiet-machine.md`](../docs/quiet-machine.md).

## What the machine is now

One card. `nvidia-smi` lists the A6000 at `61:00.0` and nothing else; both
`llm-*-3090` units are disabled, the Telegram gateway is up with no model
server behind it, and the lease is free. Moving the agent's Qwen profile to
the A6000 is one environment variable (`GPU=<A6000 UUID>`), but the A6000 is
also what every generation runner waits for, so that is a scheduling decision
rather than a config change.
