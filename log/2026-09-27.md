## ik DSpark 드래프트의 SwiGLU clamp — 걸리지만 수락률은 그대로 (ik_llama.cpp#2546)

질문은 ik main(`ed27bf7e`)에서 DSV4 DSpark 드래프트가 SwiGLU clamp를 빼먹는 것이 수락률을 깎는가였다. 로더는 드래프트의 한계값(V4·V4.1 드래프트 모두 층마다 10.0)을 읽지만 `swiglu_limit()`이 dflash arch에 0을 돌려줘 드래프트 FFN이 clamp 없이 돈다. 참조 `model.py`와 exllamav3는 드래프트에도 clamp를 건다. 수정은 한 줄이다.

세 팔을 같은 명령으로 돌렸다: 수정 전(base), 수정 후(patch), 그리고 수정 경로를 타되 한계를 1e30으로 줘 clamp가 한 번도 걸리지 않는 control. patch − control이 clamp의 효과, control − base가 커널 식 순서(반올림)의 효과다. 탐욕, 프롬프트 20개, A6000, 박스 임대 아래(시간 수치는 재지 않았다).

| 모델 | 팔 | n_max 3 수락 | n_max 5 수락 |
|---|---|---|---|
| V4.1 Q3_K_M + DSpark 드래프트 | base | 1984/3417 = 58.1 % | 2137/4912 = 43.5 % |
| | control | 58.1 % (20/20 같음) | 43.3 % |
| | patch | 2023/3472 = 58.3 % | 2170/4764 = 45.5 % |
| V4 UD-Q3_K_M + V4 드래프트 | base | 2120/3480 = 60.9 % | 2278/4886 = 46.6 % |
| | patch | 20/20 같음 | 한 프롬프트만 수가 다름(반올림) |

V4.1에서 clamp는 실제로 걸려 20개 중 16개 프롬프트의 드래프트를 바꿨지만, 판정 항목인 n_max 3의 풀링 수락률 차이는 +0.2 pp [−2.2, +2.1](95 % bootstrap)로 0과 구별되지 않는다. n_max 5의 +2.0 pp [+0.1, +4.1]도 부호 검정이 유의하지 않아(9 / 5 / 6, p = 0.42) 주장하지 않는다. 카드의 예측 대역 +1…+6 pp는 빗나갔다 — 틀린 항은 "clamp가 걸리면 수락이 오른다"는 사전값이었다. V4 드래프트에서는 이 프롬프트들에 clamp가 한 번도 걸리지 않았다. V4.1 base 수치는 09-25의 [PR 트리 재측정](2026-09-25.md#ik-dspark-not-lossless)과 정확히 같다(ik main 11커밋 이동 뒤에도).

PR은 이득이 아니라 참조와 맞추는 수정으로 냈다.

예측은 빗나갔다. 틀린 항은 V4.1의 편중을 GLM에 그대로 옮긴 것이다 — GLM 라우터는 부하를 더 고르게 나눈다. 그래도 목록은 균등의 2.1배다. 이 몫으로 호스트가 토큰당 읽는 바이트는 5.15 GB에서 약 2.83 GB로 줄고, 디코드 스텝은 +38…+50 %[유도]로 빨라진다. 이 값은 다음 A/B 카드의 대역(+32…+63 %) 안이지만, 디코드에서 실제로 맞는 비율은 held-out보다 낮을 수 있다(V4.1에서 그랬다). 그것은 A/B가 잰다. 벽시계도 예측(15–25분)보다 짧았는데, GLM의 MLA 층이 11개뿐이라 V4.1 산문(66.5 tok/s)보다 빨랐다.
