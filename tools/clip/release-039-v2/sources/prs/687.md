# #687 gpu: run routed NVFP4 prompt GEMM on FP4 tensor cores (@juliankang4, MERGED)

Qwen3.8 NVFP4 모델의 routed expert prompt GEMM을 GB10의 FP4 텐서 코어(block-scaled MMA)로 실행해 prefill과 첫 토큰까지의 시간을 줄입니다.

Part of #565.

## What and why

On a GB10 the routed expert products of an NVFP4 model run on INT8 tensor cores in the prompt path: each NVFP4 weight is expanded to Q8 values and multiplied with Q8 activations. GB10 has FP4 tensor cores with block scaling, so the 4-bit weights can be multiplied directly.

This PR adds a native routed NVFP4 prompt kernel to the shared `Gemm32Kernels` owner in `crates/gpu/src/gemm/nvfp4mma.rs`.

1. The kernel computes 128 output rows per tile over the existing 64 route slots. It stages tiles through shared memory with vector loads and double buffering, prefetches the next tile into registers, loads fragments with `ldmatrix`, and repacks weight nibble pairs with byte permutations. It reuses the existing route list and fault owner, so there is no second expert routing list.
2. Activations are quantized to FP4 beside their Q8 form. A fused producer visits the live columns of the selected routes, skips HOST selections, and computes SiLU, Q8 and FP4 in one launch. It packs the Q8 values it just produced, so the fused and the plain producer share one rounding rule. `GemmAct32::new_routed_for` allocates the FP4 representation only when the resident routed format is NVFP4; other formats keep their Q8 storage.
3. One scale owner, `scaled_sum` in `crates/gpu/src/gemm/grouped.rs`, applies the weight, activation and expert scales for every NVFP4 product. Ordinary inputs keep the F32 multiply and FMA rounding. When an intermediate product would overflow or underflow, it multiplies the original operands in F64 and narrows after the last scale, so a finite result stays finite. The native kernel's two output stores, the plain and fused Q8 reconstruction, the W4A8 path and the grouped epilogues all call it. The W4A8 NVFP4 accumulator is F64 because the expert scale is applied after the sum.
4. `crates/gpu/build.rs` enables the kernel for explicit `sm_120a/f` and `sm_121a/f` builds. Other targets keep the existing path.

This is a W4A4 product: the activations round to FP4 where the existing path keeps Q8. The faster path is the default, and the existing oracle bands, which this PR does not change, still pass. KL against the oracle is reported below as a diagnostic.

Release notes: Changed: routed NVFP4 prompt products run on the FP4 tensor cores of a GB10, which speeds up prefill.

## Code shape

- [x] **No second copy.** The kernel lives in the shared GEMM owner and reuses the existing route, Q8 quantization, activation and fault owners. The fused and the plain producer call one Q8-to-FP4 packer.
- [x] **Model code holds only architecture facts.** The dispatch keys on the resident routed format and the CUDA target, not on a model.
- [x] **Dead code is gone.** The new constructors have production callers.
- [x] **No silent failure.** Shape, route and fault checks stay in place; the grid size multiplication is checked. A decoded scale in the subnormal range is rescaled by exactly 2^24 before its reciprocal, so it cannot overflow.
- [x] **Comments state what is true now.** The shared-stage comments state the allocation and its bounds.
- [x] **No relaxed gate.** No band, tolerance or oracle pin moved. The unsafe ratchet row and its `PIN` explanation follow the added `unsafe` blocks, each with a `SAFETY` line.
- [x] `cargo fmt` and `cargo clippy` are clean on what I touched.

Duplication found or removed (`path:line`), or "none": none. `packed_pair` (`crates/gpu/src/gemm/nvfp4mma.rs:251`) permutes FP4 nibbles with integer register operations and the INT8 MMA helper (`crates/gpu/src/gemm/gemm32.rs:222`) multiplies INT8 fragments, so their PTX operations differ. The all-columns and the selected-columns entries (`nvfp4mma.rs:297`, `nvfp4mma.rs:317`) call the same `fused_swiglu`.

### Prefill and decode

One server load per arm, base then head, two requests per load. The prompt is a 4096-token code window (corpus offset 20480), 8 tokens are generated at temperature 0 with top-k 1, with no draft, no RAM cache, one request at a time and `--ctx-size 4224`. Model `nvidia/Qwen3.8-Flash-Next-NVFP4` at `fc694b54fb0174e0913e6adf86691ef85a4ead47`, on one GB10 with driver 595.84, CUDA 13.3 and release binaries built with `cargo oxide build --arch sm_121a`. The first request of each load includes first-use effects.

## What I ran into

This does not block the PR. KL against the oracle is higher on the head than on the base for the one-ubatch and position 3000 sets, as expected when activations round to FP4. The oracle's argmax and margin checks pass on every set. The timing is two requests per arm on one prompt, not a long benchmark.

One NVIDIA DGX Spark (GB10), driver 595.84, CUDA 13.3, with CUDA 13.3.1 in the build image.
