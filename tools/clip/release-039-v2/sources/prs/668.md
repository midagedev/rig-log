# #668 gemm: BF16 tensor cores for GB10 dense prompt products (@juliankang4, MERGED)

GB10에서 BF16, MXFP8 E4M3, FP8_B128 가중치의 prompt 곱을 BF16 tensor core를 쓰는 본체 하나로 계산해 4K prefill을 높입니다.

## What and why

On GB10, dense prompt products for BF16, MXFP8 E4M3 and FP8_B128 weights ran on exact F32 FMA tiles. This PR sends those three formats through one BF16 tensor-core body with F32 accumulation, using 64 by 64 output tiles and a permutation of the shared-memory rows that spreads fragment loads across banks. Stored weights are not rewritten, and other devices keep their current dispatch. A block-wide vote finds every tile that saw a non-finite or out-of-range operand (a magnitude above 2^47, or a subnormal) or a partial sum outside the F32 range. Only those tiles are replayed with the existing exact F32 tile reduction, so their output is the same as on the exact path. A product still takes one launch and no new global scratch buffer. I also tried keeping the partial sums in F64 instead of replaying; it needed 154, 148 and 148 registers and one block per SM, and it still failed the case where the exact path's lane-ordered F32 sum overflows to NaN, so it is not used.

On one GB10, a 4096-token prompt prefilled 98.2% faster on the NVFP4 checkpoint and 54.0% faster on the FP4-Local checkpoint (table below).

- [x] **No second copy.** The BF16, MXFP8 and FP8_B128 wrappers all call `bf16_mma_body`. The duplication scan below found only typed ABI wrappers and launchers.
- [x] **Model code holds only architecture facts.** No model code changes, and the common owners gained no per-model branch.

Duplication found or removed (`path:line`), or "none": none duplicated. ### 4K prefill timing

Each checkpoint ran as a pair on the same GB10: the baseline build first, then the candidate, each loaded once and sent one 4096-id code-fn request that generated two tokens. Concurrency was 1, drafting was off, the window was [0, 4096], and both arms used identical stored weights. Prefill tok/s is `4096 / TTFT`. The NVFP4 baseline is main plus the unmerged branches that checkpoint needs to load. The FP4-Local baseline is main plus #649 and the unmerged checkpoint-folder commits its per-layer embedding reader needs. Each checkpoint compares only with its own baseline.

| Checkpoint | Arm | Build | TTFT | Prefill |
| --- | --- | --- | ---: | ---: |
| NVFP4 | baseline | main + loading branches | 10.414 s | 393.3 tok/s |
| NVFP4 | candidate | baseline + this PR | 5.253 s | 779.7 tok/s |
| FP4-Local | baseline | main + #649 + folder commits | 8.252 s | 496.4 tok/s |
| FP4-Local | candidate | baseline + this PR | 5.358 s | 764.5 tok/s |

Prefill rose from 393.3 to 779.7 tok/s on NVFP4 (+98.2%) and from 496.4 to 764.5 tok/s on FP4-Local (+54.0%) [derived]. TTFT fell 49.6% and 35.1% [derived]. Each arm is one request after one server load, so these are single observations with no spread and no significance claim.

To check that the exact replay costs nothing on the normal path, I compared the revision before it with this one on NVFP4 (one load and two 4096-token requests each, same GB10). On the second request the earlier revision prefilled at 755.94 tok/s and this one at 774.78 tok/s, so there is no regression. The first request of the earlier revision was slower than its second, and I do not count that as a gain.

### Correctness

- FAIL-first: with the widened MMA output store replaced by zero, the oracle gate exited 1. With the output buffer left uncleared before graph replay, the gate reports `eager_graph_bits=false FAIL` and exits 1. On the previous revision, the cancelling-pair cases (between fragments, between stages, across a reused pipeline slot, warp corner, tile corner) and the NaN case read `range=false` for all three formats and the gate exits 1 (`gate_gemm ran 11 s (exit 1)`). With the replay every one of them reads `range=true past_end_untouched=true eager_graph_bits=true` and matches the exact tile bits.
- Coverage includes ragged rows and columns, 513-column raster tails, graph replay with sentinels, invalid spans, unsupported K, and extreme and subnormal E4M3 scales. The original exact tile checks stay enabled.
- Softmax KL is measured on kernel outputs against the released Q8_0 weight and int8-activation representation, next to a derived f64 oracle band. These are not whole-model KL results.
- On sm_121, each of the three entries uses 256 threads and 49,152 bytes of shared memory, with no local depot and zero spill. The BF16, FP8_B128 and MXFP8 entries use 121, 114 and 114 registers and fit two blocks per SM, against 124, 126 and 126 registers before the replay.
- Not run: GB10 is the only card used. No cc 8.6 hardware ran this, and there was no GLM or TP=2 run. GLM's wide dense FFN reaches this dispatch through `site::gated`, but its `GemmFront` supplies only quantized inputs, so the new path would not serve it until that frontend passes the common F32 form.

## What I ran into

This does not block the PR. The full `just gate-gpu-gemm` without `--case` stops before its first case on this machine because it reads model-derived inputs this machine does not have: `gate_gemm: io error: No such file or directory`. The cases this PR adds are the `dense_mma` ones in GPU Evidence.
