# #682 qwen38: load the checkpoint folder MTP draft in its stored formats (@juliankang4, MERGED)

Qwen3.8 FP4-Local 체크포인트 폴더에 들어 있는 MTP draft를 저장된 형식 그대로 읽어 켜는 작업이고, 코드 입력에서 decode가 최대 71.84% 빨라집니다.

## What and why

Part of #565. This closes the line in its section 4: "MTP draft from the FP4-Local checkpoint: W4A16_NVFP4 experts and BF16 dense parts".

`nvidia/Qwen3.8-Flash-Next-FP4-Local` ships its MTP layer inside the checkpoint folder: BF16 dense matrices, W4A16_NVFP4 routed experts with their tensor-scale companions, and F32 injects. The folder path refused a draft, so MTP on this checkpoint needed a separate GGUF draft. Now both serving entry points find the folder's draft and run it without a prepare step.

What the PR changes:

- The Qwen mapper shares one target and draft layer mapping, places the MTP layer after the trunk, joins `fc_embedding` before `fc_hidden` along the input columns, and applies the existing zero-centered norm transform.
- The folder exposes a synthetic MTP header and one shared part source. Each load filters that source to its own plan with `model::part::Filtered`, so the target plan never sees MTP tensors and the draft plan never sees trunk tensors. Strict OnCard placement checks are unchanged.
- MTP planning accepts stored BF16 dense matrices, routed NVFP4 and FP8_B128 experts, direct F32 injects, and the routed tensor-scale companions, which are not counted as experts.
- The resident selected-row site gains NVFP4 rows read with unquantized F32 activations. It reuses `RowValues`, the E2M1 table, the E4M3 decoder, the lane accumulation and the existing fault owner. The new kernel entry has its PTX shape pins.
- An explicit GGUF draft override still works. The folder's residency refusal is unchanged.

Existing paths: a GGUF draft and a folder served with draft off load through the same code as on main. There are no TP protocol changes, and draft limits for several ranks are unchanged.

Release notes: Added: MTP draft served directly from the Qwen3.8 FP4-Local checkpoint folder, with decode up to 71.84% faster on code at one request.

## What I ran

### Decode, draft off against native MTP

One DGX Spark, one slot, `nvidia/Qwen3.8-Flash-Next-FP4-Local` at `b9ce18a6`, C@1. Each request processes 4096 prompt ids with no cache hit and generates 128 ids, on four corpora. There are two alternating rounds with one request per corpus per round, so eight matched windows per mode. The table gives the median decode tok/s of the two rounds, and the draft ids accepted over drafted, summed over both rounds.

| Corpus | Draft off tok/s | Native MTP tok/s | Decode delta | Accepted / drafted |
| --- | ---: | ---: | ---: | ---: |
| code-fn | 29.77 | 45.03 | +51.24% | 160/248 (64.5%) |
| code-js | 29.79 | 51.19 | +71.84% | 171/215 (79.5%) |
| prose-en | 29.86 | 31.44 | +5.28% | 109/325 (33.5%) |
| prose-ko | 29.76 | 37.98 | +27.63% | 122/194 (62.9%) |

Decode delta per corpus: code-fn +51.24%; code-js +71.84%; prose-en +5.28%; prose-ko +27.63%.

All 1024 generated token ids per mode (8 windows of 128) equal the draft-off ids, with 0 mismatches and 0 errors. Two rounds make this a short comparison: the numbers are decode-rate gains at one request, not a long-run confidence claim.

The decode gain does not carry over to the whole request on every corpus. Median full-request time, draft off against native MTP, is 12328 against 11105 ms on code-fn, 12333 against 10777 ms on code-js, 12206 against 12285 ms on prose-en and 12250 against 11646 ms on prose-ko. Median time to first token rises from about 7.9 to 8.0 s with draft off to about 8.2 to 8.3 s with MTP.

The plain-read ceiling on the node was 239.3 GB/s before the sitting and 240.3 GB/s after.

## What I ran into

None of this blocks the PR.

- The sm_86 PTX pin rows for the new entry hold ptxas values measured on a GB10 (`regs=40`, `spill=0`, no depot, no local loads or stores, `reqntid=256`). The cc 8.6 driver JIT was not measured, and the pin says so.
- English prose accepts 33.5% of its drafted ids, against 79.5% on code-js, so its decode gain is 5.28% and its full-request time does not improve.
- The stored draft head is about 0.36 GiB read per proposal, against about 0.17 GiB of dense weights and 0.026 GiB of selected routed weights (derived from the checkpoint shapes).
