# #660 qwen38: read NVFP4 PLE planes from a checkpoint folder (@juliankang4, MERGED)

Qwen3.8 FP4-Local 체크포인트 폴더를 분할 파일로 바꾸지 않고 그대로 불러올 수 있게, 값과 스케일이 따로 저장된 NVFP4 PLE 행을 폴더에서 직접 읽습니다.

Part of #565.

## What and why

A Qwen3.8 FP4-Local checkpoint folder now loads with `-m <folder>`, without first being prepared into a split. The folder stores its per-layer embedding (PLE) table, `per_layer_token_embd.weight`, as NVFP4 rows in two planes: the 4-bit codes (80 B for a 160-value row) and the block scales (10 B). A folder load used to read only F8 PLE rows, so it refused this table with `(nvfp4_rows) is stored in another layout: prepare the folder into a split`.

This PR reads both planes where the checkpoint stores them. The existing row table and prefetcher gather the two planes. One decoder and one rounding rule serve the packed rows of a split and the separate planes of a folder, so a row decodes to the same bits from either layout. The folder normalizer and the folder reader share one ModelOpt metadata check for these rows, and the refusals for a wrong width, row count or scale are kept.

The planner keeps a PLE table read from a checkpoint folder on NVMe, even when the unified memory pool could hold it, the same way it treats a split's NVMe table. A host-resident copy would keep that memory for the whole run. Its page-cache reserve counts both planes, since one row read touches a page of the code plane and a page of the scale plane. Ordinary, node-assigned and multi-slot plans all go through one row placement owner. A mapped split keeps its room-dependent placement, and a hand-written Host plan for a folder table still gets its named `OnCard`/`PleHost` error.

Release notes: Added: A Qwen3.8 FP4-Local checkpoint folder loads directly, with its NVFP4 PLE table read from the folder's value and scale planes.

## Code shape

- [x] **No second copy.** The folder reader, `RunTable`, the prefetcher and the NVFP4 group decoder are the existing ones. The packed and the separate layout share one decoder and one metadata check.
- [x] **Model code holds only architecture facts.** The Qwen folder reader names the PLE source ranges. The plane layout and the placement policy live in the common model, GGUF and placement code.
- [x] **Dead code is gone.** The blanket refusal of stored NVFP4 rows is replaced by plane support. The old alignment and scale refusals moved into `group_count` and `decode_groups` and still fire.
- [x] **No silent failure.** Short planes, wrong widths, row totals and invalid scales fail with named errors.
- [x] **Comments state what is true now.**
- [x] **No relaxed gate.** No band, tolerance or lint level moved.
- [x] `cargo fmt` and `cargo clippy` are clean on what I touched; the lint count did not go up.

Duplication found or removed (`path:line`): none. Ten new items (the plane descriptor, the row-table list, the shared scale check, the plane decoder, the backing getter and the source placement entry among them) were checked against the existing owners.

## What I ran into

This does not block the PR. A separate-plane row has the same logical payload as a packed 90 B row, but its two reads may cost a different amount of page I/O on NVMe. The short run above shows no difference in speed, and I did not measure per-read cost. I measured nothing on two DGX Sparks. The loader this PR extends is the one the GLM FP4-Local folder load already uses, and no rank count, kernel or GLM behavior changes here.
