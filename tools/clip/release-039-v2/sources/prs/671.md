# #671 serve: flush each completed prompt before the next call (@juliankang4, MERGED)

서버가 새 prompt 작업을 시작하기 전에 이미 만들어진 token을 먼저 클라이언트로 보내서, 동시 요청의 중간 응답이 기다리는 시간을 줄입니다.

Part of #565.

## What and why

With several requests in flight, the serve worker started the next prompt before it sent the tokens that were already ready. A request that had finished its prompt waited behind every prefill that was still queued. The worker now sends ready tokens after each completed prompt start, each completed prompt plan and each decode round, before it seals a cache or runs more prompt work.

`pump_ready` reuses `pump_at`, so completion, cancellation and error handling stay in one place. `take_need` gives the turn-based worker the same cached-need consumption. No model, kernel, device allocation, rank constant or public API changes. The worker is shared by every model seat, and no model code changes.

On one DGX Spark with four concurrent 4096-token requests, the median request TTFT fell from 43.925 s to 20.399 s (-53.56%, one main/head pair). The responses now arrive one after another as each prefill finishes, where on main three of them arrived together after the last prefill. Greedy output is identical on all six request pairs.

Release notes: Changed: the server sends ready tokens before it starts another prompt, which lowers the TTFT of the middle requests in a concurrent batch.

### Correctness

- All six request pairs returned the same 128 greedy ids on main and head.
- FAIL-first, five cases. The new regression fails on main (`FAIL-FIRST main rc=101`) and on a variant that drains only before the admission list (`FAIL-FIRST initial fix rc=101`). Removing each of the three drain calls fails it too: after a completed decode (`completed decode rc=101`), after a new prompt (`new prompt rc=101`) and after a prompt's last part (`last prompt part rc=101`). Restored code passes.
- The regression uses the existing mock with four resident slots. It checks that an existing decoder's token is delivered before the newcomer starts, that a completed whole prompt is delivered before the next prompt, and that a completed final quantum is delivered before another long quantum. It counts non-empty token payloads, not empty prompt heartbeats.
- Two JSON-schema streams that both need a fill: a second regression holds B's fill after A's final fill and checks that A's text reaches the client first. It passes on the head (`1 passed; 0 failed`). With the new four-line pump after each fill removed, it fails at the delivery assertion (`panicked at crates/serve/tests/slots/yields.rs:736`), and the eleven `slots::yields::` tests pass again once the line is restored.
- `cargo test -p bloomery-serve`: 344 unit tests pass.
- No arithmetic changed, so no oracle or KL measurement was added. The mock covers four resident slots, and no multi-GPU run was made.

## What I ran into

This does not block the PR. Prefill of the queued prompts is still serial, so the last response of a group of four still arrives at about 33 s. Changing prompt quanta or mixed prompt and verify passes would be separate work.
