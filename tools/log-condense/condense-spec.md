# 로그 통폐합·축약 라운드 — 공통 스펙

리포: `/Users/hckim/repo/rig-log` (한 워크스테이션의 측정 로그, 한국어). 지금 `log/`에는 실험당 한 파일이 있어 하루에 15개까지 쌓였다. 이 라운드는 **하루치 파일 여러 개를 날짜 파일 하나로 합치고, 내용을 크게 줄인다.** 너는 날짜 하나만 맡는다(아래 "네 날짜").

## 산출물

`/Users/hckim/repo/rig-log/log/2026-09-DD.md` 새 파일 하나. 다른 파일은 쓰지도 지우지도 않는다(옛 파일 삭제·링크 재작성·README는 리드가 한다).

형식:

```markdown
# 2026-09-DD

<그날 전체를 두세 문장으로: 무엇을 했고 무엇이 판명됐나. 대표 수치 하나 이상.>

<a name="<slug>"></a>
## <원래 제목을 짧게>

<본문: 산문 문단 1~3개 + 필요하면 핵심 표 하나>

원본: `git show c27c3a7:log/<옛 파일명>`

<a name="<다음 slug>"></a>
## ...
```

- `<slug>` = 옛 파일명에서 `2026-09-DD-`와 `.md`를 뺀 것 그대로(예: `2026-09-21-k-the-guard-was-inside-the-loop.md` → `k-the-guard-was-inside-the-loop`). 옛 파일마다 절 하나, 원래 순서대로.
- `원본:` 줄은 절마다 필수. 지운 세부는 이 줄로 git 이력에서 복원 가능하다 — 그래서 과감히 줄여도 된다.

## 분량

- **날짜 파일 전체 ≤ 옛 파일 합계 바이트의 20%** (게이트가 잰다). 목표는 12–15%.
- 절 하나는 대체로 800–2,500바이트. 절의 뼈대는 **질문 → 한 일 → 숫자 → 판명된 것/틀렸던 것**.
- 표는 결론을 떠받치는 행만 남긴다(보통 3–6행). 스텝별 연대기, 빌드 번호 이야기, 중간 가설 전개, 반복되는 방법론 설명(이미 docs/에 있는 것)은 버린다.
- 명령줄은 절마다 **대표 하나까지**(재현에 결정적인 플래그가 있는 경우만). 나머지는 원본 줄이 진다.
- 이미지·클립 임베드(`![...](../assets/...)`)는 그 절의 대표 하나만 남긴다.

## 보존해야 하는 것 (이 리포의 규율 — 줄여도 이건 남긴다)

1. **측정한 숫자만.** 새 숫자를 만들지 않는다. 반올림·합산·비율 계산도 금지 — 원문에 적힌 숫자 문자열을 그대로 쓴다(게이트가 새 파일의 모든 숫자가 옛 파일에 있는지 잰다).
2. **숫자마다 조건 한정어를 같은 문장에 붙여 둔다**: 어느 카드(A6000/3090/CPU), 어느 엔진(ik_llama.cpp/mainline/bloomery/mistral.rs…), 핵심 플래그(`-ngl 0`, ik 기본값 vs 최속 조합 등), 컨텍스트 깊이, 스레드 수. 축약에서 가장 쉽게 생기는 오류가 조건이 다른 두 숫자를 한 문장·한 표에 섞는 것이다. 원문이 구분한 것은 구분한 채로 둔다.
3. **틀렸던 것을 남긴다.** 원문의 정정(`~~취소선~~` + 정정문)은 쌍으로 전부 보존한다 — 문장은 줄여도 취소선과 정정은 남긴다. 기각된 가설, 느려진 실행, 실패한 시도도 한 문장씩 남긴다. 이긴 결과만 남은 기록은 광고다.
4. **업스트림 링크**(github.com/…/pull/N, …/issues/N)는 전부 남긴다.
5. 링크: 다른 로그를 가리키는 링크는 새 형식으로 쓴다 — `2026-09-XX.md#<slug>` (매핑표: `/Users/hckim/repo/rig-log/log/moved.tsv`, 왼쪽 옛 파일명 → 오른쪽 새 대상). 2026-09-22 파일들은 이번 라운드 대상이 아니니 그 링크는 옛 형식 그대로 두어도 된다(게이트가 잡으면 보고에 적어라). `../docs/…`, `../tools/…`, `../assets/…` 링크는 그대로 두되 대상이 실존해야 한다.

## 문체

- 한국어. **발견은 산문, 측정은 표.** 불릿 목록으로 쪼개지 않는다.
- 번역투·명사 나열 금지. 짧은 평서문. 원문의 좋은 문장(특히 절 제목과 결론 문장)은 살려 쓴다.
- 새 해석·새 결론을 보태지 않는다. 원문에 없는 인과를 쓰지 않는다.

## 금지

- git 상태 변경 전부(commit/push/checkout/stash/restore/add/rm/mv). 읽기 전용 `git log`/`git show`/`git diff`만.
- 네 날짜 파일 외의 파일 생성·수정·삭제. 옛 로그 파일은 읽기만.
- 게이트 스크립트·매핑표 수정.
- 다른 에이전트에게 SendMessage 금지. 질문은 리드에게만.
- 사용자 직접 지시가 이 스펙과 충돌하면 사용자 지시를 따르고 보고에 한 줄 적는다.

## 보고 (마지막 메시지로 — 파일로 쓰지 말 것)

1. 만든 파일 경로와 바이트 수, 옛 합계 대비 비율.
2. 게이트 실제 출력 전체(붙여넣기).
3. **의도적으로 버린 것 목록** — 절마다 한 줄(예: "빌드 1–9 연대기", "스레드 스위프 표 12행 중 9행"). 리드가 이 목록으로 "괜찮은 버림"인지 판정한다.
4. 자기 독해 체크 결과(조건 한정어·정정 쌍·새 주장) — 걸린 곳이 있었으면 무엇을 고쳤는지.
5. 원문에서 발견한 모순·오류(서로 다른 파일이 같은 숫자를 다르게 적은 곳 등) — 고치지 말고 보고만.
6. 지정한 것 이외에 개선 여지가 보인 곳: `path:line` + 한 줄 + 대략의 크기. 보고만, 손대지 말 것.
