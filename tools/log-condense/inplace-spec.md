# rig-log 날짜 파일 하나를 제자리에서 줄이는 라운드

리포: `/Users/hckim/repo/rig-log`. 한 워크스테이션의 측정 로그이고, 한국어로 쓴 공개 리포다. 09-23부터 09-29까지는 다른 세션(bloomery 엔진 개발)의 작업 기록이 그대로 흘러들었다. 그 결과 절 하나가 평균 2.7 KB가 됐고, 제목은 문장처럼 길어졌으며(중앙값 62–83자), 본문에는 라운드 이름·시팅 번호·절 간 참조가 설명 없이 박혔다. 사람이 절 하나만 열어서는 읽을 수 없다. **너는 날짜 파일 하나를 맡아 사람이 읽을 수 있게 다시 쓴다.** 날짜는 프롬프트 끝에 있다.

## 산출물

`<scratch>/condense/<날짜>.md` 파일 하나. 리포 안의 파일은 **읽기만 하고, 만들거나 고치지 않는다.** 반영은 리드가 한다. 하네스가 파일 쓰기를 거부하면 마지막 메시지에 파일 전체를 `=====BEGIN FILE=====`와 `=====END FILE=====` 사이에 넣는다.

원본은 `/Users/hckim/repo/rig-log/log/<날짜>.md`이고, 커밋 `42026b2`에 그대로 있다.

## 형식

```markdown
# 2026-09-DD

<그날 전체를 서너 문장으로. 무엇을 했고 무엇이 판명됐는지, 대표 수치 하나 이상. 카드·엔진·모델을 문장 안에 밝힌다.>

원본: `git show 42026b2:log/2026-09-DD.md`

<a name="<옛 slug>"></a>
## <짧은 제목>

<본문>
```

- **옛 앵커는 전부 남긴다.** bloomery 리포의 문서가 `2026-09-DD.md#slug`로 인용하므로 하나라도 빠지면 링크가 죽는다. 같은 주제의 연속 라운드(같은 커널을 여러 번 고친 절, 같은 레버의 시팅 여러 번)는 **한 절로 합쳐도 된다.** 합칠 때는 옛 앵커를 `## ` 바로 위에 줄마다 하나씩 쌓아 둔다. 진행은 표 하나(단계 | 숫자)로 보여 준다. 합치기가 가독성의 가장 큰 레버다. 억지로 합치지는 말고, 독자가 한 이야기로 읽을 수 있는 것만 합친다.
- 절 순서는 원문 순서를 따른다(합친 절은 첫 절 자리에 둔다).
- `원본:` 줄은 머리 문단 바로 뒤에 한 번만 쓴다.

## 분량과 모양 (게이트가 잰다)

- 절 하나는 **2,500 B 이하(UTF-8, 한글 한 자가 3 B)**, 목표는 1,200–1,800 B다. 합친 절도 같은 한도를 지킨다.
- 제목은 **60자 이하**이고, 목표는 40자 이하다. 제목은 목차 역할이다. 숫자와 결론은 본문 첫 문장에 쓴다. 원문 제목에 `~~취소선~~`이 있으면 그 span을 글자 그대로 본문 첫 줄로 옮기고, 제목은 정정된 내용으로 짧게 쓴다.
- 파일 전체는 원본 바이트의 **45% 이하**, 목표는 30–40%다.
- 절의 뼈대는 **질문 → 한 일(조건: 카드, 엔진, 모델, 깊이·P, 바퀴 수) → 숫자 → 판명된 것·틀렸던 것** 순서다.

## 은어를 없앤다 — 이 라운드의 핵심

- bloomery 라운드·시팅 이름(`ds41bulk`, `q3gemmb`, 시팅 14, `plan (a)`, `E21`, `dsres`, `tl37` 같은 것)은 **처음 나올 때 무엇인지 한 구절로 풀고**, 필요 없으면 지운다. 커밋 해시는 코드 상태를 가리키는 데 꼭 필요할 때만 한 번 남긴다.
- `#slug` 참조로 문장을 잇지 않는다. 다른 절을 가리켜야 하면 `[무엇](2026-09-DD.md#slug)`처럼 무엇인지 말로 쓰고 링크한다.
- `[유도]` 예측 전개, 시팅 운영(임대 시각, loadavg·IO 압력 증인 값, 러너 명령줄 여러 개), 커밋별 경과는 bloomery 쪽 상세다(사용자 결정 2026-09-30: "bloomery 라운드의 상세는 bloomery에, 여기에는 짧은 절과 링크"). 지우고 `원본:` 줄에 맡긴다. 예측이 **맞았는지 틀렸는지**는 판명의 일부이므로 한 문장으로 남긴다("예측 41–45 안", "예측 대역 아래"처럼).
- 원문이 bloomery 문서 경로(`docs/…`)를 가리키고 그 파일이 `/Users/hckim/repo/bloomery/<경로>`에 실제로 있으면 `https://github.com/midagedev/bloomery/blob/main/<경로>`로 링크해도 된다. 확인하지 않은 경로는 링크하지 않는다.
- 명령줄은 절마다 재현에 결정적인 것 하나까지만 둔다. 보통은 0개다.

## 보존 (이 리포의 규율 — 줄여도 이것은 남긴다)

1. **측정한 숫자만.** 새 숫자를 만들지 않는다. 반올림·합산·비율 계산도 금지이고, 원문에 적힌 숫자 문자열을 그대로 쓴다(게이트가 새 파일의 모든 숫자가 원문에 있는지 잰다).
2. **숫자마다 조건을 같은 문장이나 표 머리에 붙인다**: 카드(A6000/3090), 엔진(bloomery/llama.cpp/ik/mistral.rs), 모델, 깊이·P, 표지(`[cpu-busy]`, `[cold]`). 조건이 다른 두 숫자를 한 문장·한 표에 섞는 것이 축약에서 가장 흔한 오류다. 합친 절에서 특히 조심한다. 원문이 "한 표에 두지 않는다"고 한 것은 합치지 않는다.
3. **틀렸던 것을 남긴다.** 원문의 `~~취소선~~`은 span마다 **글자 그대로** 남기고, 그 뒤의 정정문도 남긴다(문장은 줄여도 된다). 새 취소선은 만들지 않는다. 기각된 가설, 느려진 실행, 예측이 빗나간 것도 한 문장씩 남긴다. 이긴 결과만 남은 기록은 광고다.
4. **업스트림 링크**(`github.com/…/pull/N`, `…/issues/N`)는 전부 남긴다.
5. 상대 링크(`../docs/…`, `2026-09-DD.md#…`)는 그대로 두되, 대상이 실제로 있어야 한다.

## 문체

- 한국어로, 짧은 평서문으로 쓴다. **발견은 산문으로, 측정은 표로.** 불릿으로 쪼개지 않는다.
- 번역투와 명사 나열을 피한다. 원문의 좋은 결론 문장은 살려 쓴다.
- 새 해석이나 새 인과를 보태지 않는다. 원문에 없는 주장을 만들지 않는다.
- 독자는 이 기계의 주인이다. LLM 추론, GPU, MoE는 알지만 bloomery의 라운드 이름은 모른다고 생각하고 쓴다.

## 금지

- git 상태를 바꾸는 명령 전부(commit/push/checkout/stash/restore/add/rm/mv). 읽기 전용 `git log`/`git show`/`git diff`만 쓴다.
- 산출물 파일 밖의 파일 생성·수정·삭제. 리포는 읽기만 한다.
- 게이트 스크립트 수정.
- 다른 에이전트나 세션에 SendMessage를 보내지 않는다. 은퇴한 에이전트에게도 보내지 않는다. 질문은 리드에게만 한다.
- 사용자의 직접 지시가 이 스펙과 충돌하면 사용자 지시를 따르고, 보고에 한 줄 적는다.
- 대기 루프에서 `pgrep -f`로 자기 자신을 기다리지 않는다(이 라운드는 기다릴 일이 없다).

## 보고 (마지막 메시지로 — 파일로 쓰지 말 것)

1. 산출물 경로, 바이트 수, 원본 대비 비율, 절 수(원본 → 새), 합친 절 목록(어느 앵커들을 한 절로).
2. 게이트 출력 전체(붙여넣기).
3. **의도적으로 버린 것** — 절마다 한 줄(예: "시팅 14 증인 블록", "예측 유도 두 문단", "러너 명령줄 셋").
4. 자기 독해 체크 결과 — 걸린 곳이 있었다면 무엇을 고쳤는지.
5. 원문에서 발견한 모순·오류(같은 숫자를 절마다 다르게 적은 곳 등). 고치지 말고 보고만 한다.
6. 지정한 일 밖에서 개선 여지가 보인 곳: `path:line` + 한 줄 + 대략의 크기. 보고만 하고 손대지 않는다.
